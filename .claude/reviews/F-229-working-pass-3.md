## Defects

### D1, a long valid header still makes `read_header` quadratic: a 275 KB frame holds the decoder for 108 seconds
**Where**: `crates/ocelli-codec/src/jpegxl.rs:262` to `:295` (`read_header`), unchanged by this round
**What**: `read_header` feeds one byte per `try_init`, and each `try_init` re-parses the header from the first byte. The pre-check removed the ICC route only. A header whose length comes from extra-channel names (`Name` is up to 1,071 bytes, and up to 256 channels pass `jxl-image`'s limit) is valid, has no ICC flag, passes the pre-check in 631 microseconds, and is then re-parsed once per byte. Measured release, `JpegXlDecoder::general().decode`, 64 by 96 RGB descriptor: 8 channels (8,596 bytes) 0.115 s, 16 (17,185) 0.429 s, 32 (34,363) 1.70 s, 64 (68,719) 7.21 s, 256 (274,855) 108.4 s. Each doubling multiplies the time by about four. The decode then refuses `UnsupportedPixelFormat` from `validate_header`, because Ocelli refuses every extra channel.
**Why it is wrong**: pass 2 D5 counted exactly this mechanism, quoting `read_header` and the re-parse per `try_init`, and the brief for this pass is that D5 timing is linear. The report's "Flat" table covers ICC inputs only. One frame of a quarter megabyte holds a decode worker for nearly two minutes and is refused at the end.
**Evidence**: probe `names N`, release, scratch `target/f229-p3-scratch`. The pre-check returns `Ok(())` on every one.
**Scope and regression**: present on the tree, every `.110` and `.112` caller. Two remedies fit the existing structure: the pre-check already holds the parsed header, so it can refuse a non-empty `ec_info` as `UnsupportedPixelFormat` exactly as `validate_header` does, or `read_header` can grow its window geometrically as the pre-check does. Regression: the 64 channel stream with a time bound well under its current 7 s. Whether another header field gives the same length cheaply was not searched beyond the extension (whose skip is constant time) and the upsampling weights (fixed size).

### D2, a 1,129 byte container decodes successfully after allocating 1 GiB, because `jxl-oxide` inflates `brob` boxes in full
**Where**: `crates/ocelli-codec/src/jpegxl.rs` decode path, through `jxl-oxide` 0.12.6 `aux_box.rs:65` to `:76` and `:104` (`DecompressorWriter::new(Vec::new(), 4096)` written to without a limit), reached because `check_before_parse` passes any header without an ICC flag and `read_header` feeds the whole container to `UninitializedJxlImage::feed_bytes`
**What**: a container with the signature box, a `brob` box carrying `Exif` and 841 bytes of Brotli (1 GiB of zeros, `brotli -q 11 -w 24`), then a `jxlc` box holding `jpegxl_lossless_rgb8.jxl`, 1,129 bytes in all. `JpegXlDecoder::general().decode` returns `Ok(())` and writes the frame. One allocation of 1,073,741,824 bytes, peak heap 1,090,569,223, peak resident 1,096,925,184.
**Why it is wrong**: D-21 allows "bounded library-owned decoded storage" and names one exception, the ICC buffer that the pre-check now removes. This storage is not decoded pixels, is not seen by the `AllocTracker` the module doc at `jpegxl.rs:12` cites as the bound, and is limited only by Brotli's ratio. The ratio is about 1.3 million, so a 4 KiB frame asks for several GiB, which ends a native worker under memory pressure and exceeds wasm32 linear memory. The brief's rule is that nothing may allocate far beyond the input's size. Reading `jxl-oxide`'s `aux_box/jbrd.rs` and `jxl-jbr` 0.2.1 `lib.rs:59` shows a `jbrd` box takes the same unbounded `DecompressorWriter`, and `Padding::parse` reserves up to `2^21` bytes from a 24 bit field. Those two are read from source and not constructed.
**Evidence**: probe `brob data/zeros1g.br crafted/brob_bomb.jxl`, then `/usr/bin/time -l probe decodefile crafted/brob_bomb.jxl 64 96 3 8 8 RGB`.
**Scope and regression**: present on the tree and on `0a6a2a3`, container form only, not introduced by this round and missed by passes 1 and 2. The pre-check already walks every container event, so the smallest remedy is to refuse any auxiliary box whose content `jxl-oxide` would inflate or buffer (`brob`, and `jbrd`, which `.111` being unavailable means no Ocelli path needs), or to hand `jxl-oxide` only the collected codestream as a bare stream. Regression: this 1,129 byte container expecting a refusal, with a peak heap bound.

### D3, three sentences of `jpegxl_icc.rs` are false
**Where**: `crates/ocelli-codec/src/jpegxl_icc.rs:32` to `:37`, `:53` to `:55`, `:60` to `:62`
**What**:
(a) "Collection stops once the header has been read, so the collected prefix is bounded by the header length rather than by the input", "each probe doubles the window it will read" and "The one probe over everything collected happens only when the input is exhausted short of a decision, which is the refusal path." A bare codestream is a single `Codestream` event. When its header is longer than 64 bytes the first probe returns EOF, the loop has no further event, and the final probe copies the whole input and decides on the success path. Measured: a valid non-ICC header of 565 bytes followed by 1 MiB returns `Ok(())` after one 1,049,142 byte allocation. The same stream in 4 KiB `jxlp` boxes peaks at 1,152 bytes. The implementer's report repeats it ("nothing copies the whole codestream (N1 addressed)"). Memory stays bounded by the input, so this is a false claim and not a safety failure.
(b) "`InvalidCodestream` ... when the container structure itself is invalid." The loop stops at the first decision, so a container that breaks after the header is not seen. 13 fuzz inputs return `Ok(())` or `UnsupportedPixelFormat` on an invalid container. The decode still refuses each `Ok` one later.
(c) "The refusal kinds are the ones the decode itself returns, so only the time of the refusal changes, never the policy." On the 26 byte stream the decode without the pre-check returns `InvalidCodestream` and the pre-check returns `UnsupportedPixelFormat`. That change of kind is what `declared_icc_refuses_unsupported_before_any_parse` relies on to detect the call's removal, in its own comment.
**Why it is wrong**: microscope section 3. Each is a checkable claim about the function's contract and each fails when run.
**Evidence**: probe `bigtail` for (a), the fuzz mismatch dump for (b), the `call_removed` mutation for (c).
**Scope and regression**: prose, plus the doubling for (a). Either loop the doubling over the collected slices after the events end, which makes (a) true, or delete the sentences. Narrow (b) to the container before the end of the header. Delete (c) or say the kind can change from `InvalidCodestream` to `UnsupportedPixelFormat`.

### D4, `jxl-image` is a direct dependency nothing uses, and D-28's new sentence gives it a reason that does not hold
**Where**: `crates/ocelli-codec/Cargo.toml:24`, `Cargo.toml:178` to `:184`, `docs/hld/DEVIATIONS.md:45` (D-28)
**What**: no source in `crates/` or `examples/` names `jxl_image`. The pre-check uses `jxl_oxide::ImageHeader` (`jpegxl_icc.rs:40`), and `jxl-oxide` 0.12.6 `lib.rs:166` re-exports the whole crate, `pub use jxl_image::{self as image, ExtraChannelType, ImageHeader}`, without a feature gate. Removing `jxl-image.workspace = true` from `ocelli-codec` in a scratch copy builds, and the `jpegxl` and lib tests stay green. D-28 now says `jxl-image`, `jxl-bitstream` and `jxl-oxide-common` "are direct because the ICC pre-check parses the header with `ImageHeader::parse`, and `jxl-oxide` re-exports neither the `Bitstream` it parses from nor the `Bundle` trait that defines it". The second half justifies the other two crates and is true. It is not a reason for `jxl-image`, and the first half is satisfied by the re-export.
**Why it is wrong**: a false sentence in the normative deviation register, and an exactly pinned direct dependency with no use, which the next `jxl-oxide` bump has to keep in step for nothing. The closure is unchanged, so licences and notices are not affected.
**Evidence**: `grep -rn jxl_image crates examples --include='*.rs'` is empty. Mutation `jxl_image_dep_removed`, exit 0.
**Scope and regression**: manifest and prose. Drop the `jxl-image` entry from both manifests and from D-28's sentence, or keep it and say it is direct only to pin the version `jxl-oxide` resolves (then `jxl-render`'s precedent in the same row is the model). The sprint lead owns D-28.

### S1, the window growth that keeps a long valid header decodable is executed by no test
**Where**: `crates/ocelli-codec/src/jpegxl_icc.rs:79` (`probe_at = probe_at.saturating_mul(2)`) and the final probe on the success path
**What**: replacing the growth with `return Err(CodecError::InvalidCodestream)` leaves every `jpegxl` and lib test green. No fixture has a header longer than 64 bytes, and the one ICC test long enough is refused either way. The 565 byte header rewrite of `jpegxl_lossless_rgb8.jxl` decodes to the reference on the tree and refuses `InvalidCodestream` under the mutation, bare and in `jxlp` boxes.

**Regression**: that rewrite as a fixture expecting the reference output, bare and split over `jxlp` boxes so both the in-loop growth and the final probe run.
