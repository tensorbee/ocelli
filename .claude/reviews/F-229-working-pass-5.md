## Defects

### D1, the extraction rules test comment says every other rule has a case only it catches in the four new tests, and two of them do not
**Where**: `crates/ocelli-codec/tests/jpegxl.rs:833` to `:835`, in `containers_that_break_the_extraction_rules_refuse`
**What**: the comment ends "The other rules are mostly hidden behind a second rule here, so each of them has a case only it catches in the four tests that follow this one". The other rules it names are no codestream, two `jxlc` boxes, `jxlc` beside `jxlp`, out of order and after the final one. The four tests cover index order, `jxlp` after `jxlc`, `jxlp` after the final `jxlp` and `jxlc` after `jxlp`. The two `jxlc` rule has no case in them. Its detector is this test's own `duplicate` case: deleting it turns this test red with `left: Ok(())`, which also makes "hidden behind a second rule here" false for that case. The no-codestream rule has no detecting case anywhere. Deleting it leaves every test green, because an empty codestream fails `check_header` with the same `InvalidCodestream`, as pass 4 already found.
**Why it is wrong**: microscope sections 2 and 3, a false sentence about what a test detects. That is the class pass 4 D2 was filed for. A reader takes from it that every rule has a discriminating case, and one rule cannot have one.
**Evidence**: mutations `rule two jxlc` (red, only this test, `left: Ok(())`) and `rule no codestream` (27 passed).
**Scope and regression**: comment only, introduced this round. The smallest fix narrows the sentence to the four rules the following tests cover, says that the `duplicate` case here detects the two `jxlc` rule, and says that removing the no-codestream rule cannot be seen by kind. Deleting the sentence is also acceptable.

## Nitpicks

- **N1.** `usize::try_from(n).map_err(|_| CodecError::InvalidCodestream)?` (`jpegxl_icc.rs:215`) cannot fail on a 64 bit host, so replacing it with `unwrap_or(available)` leaves every test green. On a host, a `u64::MAX` size is refused by the `n > available` comparison, which is guarded. The branch only matters on wasm32, where `ocelli-codec` is not shipped today (D-28). The comment beside it is true.
- **N2.** Pass 4 N1, N2 and N4 are carried unchanged, as the implementer's report says. N2 was re-run: `--document-private-items` still fails on the same three links.
- **N3.** Pass 4 N3 ("The header probes allocate nothing", `jpegxl_icc.rs:47`) is carried, and the fuzz found a case without a valid extra-channel header. A 156 byte container whose 111 byte `jxlp` codestream is a garbled header that ends early peaked at 1,074 bytes beyond the input length inside `prepare` and refused `InvalidCodestream`. The constant bound the module doc gives covers it, so the sentence should say "nothing beyond the bound below".
