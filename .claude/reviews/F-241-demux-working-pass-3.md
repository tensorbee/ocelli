## Smells

### S1, num_ref_idx_l1_active_minus1 has no row, so tightening its bound stays green

**Where**: crates/ocelli-codec/src/video/h264.rs:581, with the `Craft` slice builder at :1649, which writes only I and P slices.
**What**: the lead's S1 ruling asks for every range bound to be checked at the bound and one past it. The l1 override bound, 0 to 15 for a frame under 7.4.3, was added in pass 1's remediation and has no row, because `Craft` never writes a B slice. Mutant `O3-l1-14` changes `MAX_FRAME_REF_IDX` to `MAX_FRAME_REF_IDX - 1` for l1 only, and every test still passes.
**Failure mechanism**: the mutant refuses every B slice with 16 list 1 references, which x264 `ref=16` with B-frames can write. This is the class pass 2's S1 named, a refusal of valid input that the suite cannot see.
**Fix**: give `Craft` a B slice, slice_type 6. For a B slice, 7.3.3 adds direct_spatial_mv_pred_flag, l1 in the override and a second ref_pic_list_modification, and pred_weight_table reads l1 only when weighted_bipred_idc is 1. Then add rows "override l1 15" (accepted) and "override l1 16" (refused, "num_ref_idx_l1_active_minus1 over 15").

### S2, the area row sits 4 below its bound, so `>` to `>=` stays green

**Where**: crates/ocelli-codec/src/video/h264.rs:258, with rows at :1772 to :1822.
**What**: the comment at :1772 says "area 139 264", but the accepted row is 1 055 x 132 = 139 260. A.3.1 item e is `PicWidthInMbs * FrameHeightInMbs <= MaxFS`, and MaxFS is 139 264 at levels 6 to 6.2 in Table A-1. Mutant `O3-h264-area` (`>` to `>=` at :258) survives.
**Failure mechanism**: the mutant refuses a picture of exactly MaxFS macroblocks, such as 16 384 x 2 176 (1 024 x 136 MBs), which is legal at level 6.2.
**Fix**: change the accepted row to width 1023 and height 135 (1 024 x 136 = 139 264), and keep 1 055 x 133 as the refused row.

## Nitpicks

- N1, the builders' tails are not valid syntax past the last field the demuxer reads. h265.rs:1112 writes 7 flags after chroma_sample_loc_type_bottom_field, but E.2.1 has 6 (neutral_chroma_indication_flag through bitstream_restriction_flag). The next flag is sps_extension_present_flag, so one extra 0 sits before rbsp_stop_one_bit, and `trace_headers` reports `rbsp_stop_one_bit out of range: 0` on "chroma loc 5". h264.rs:1724's filler byte 0x55 reads as slice_qp_delta +1, so "qp 25" has SliceQPY 52, outside 7.4.3's range, and ffmpeg reports `QP 52 out of range`. `vui` stops at field_seq_flag and `parse_slice` stops after dec_ref_pic_marking, so no verdict changes today. If either parser later reads further, these rows go red rather than green. Fix: `0..6` at :1112, and a filler that reads as slice_qp_delta 0, for example a leading `1` bit.
- N2, h264.rs:1570. `Craft::sps` writes no separate_colour_plane_flag when `chroma` is 3, and `slice` writes chroma_log2_weight_denom even when ChromaArrayType is 0. No row changes `chroma` from 1, so nothing is wrong today. A future 4:4:4 or monochrome row would be misaligned from the flag onward.
