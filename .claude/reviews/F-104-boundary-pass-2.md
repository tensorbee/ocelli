## Acceptance challenged

- **AC9 was executed, not read.** The remediation says the presented-event half is "unmet in Node" and "a browser-only criterion". I built the dev module and reached the published CPU-canvas path in Node 24.13.0 with `OffscreenCanvas`, `OffscreenCanvasRenderingContext2D` and `ImageData` stubs. `bindCpuCanvas` bound a 64 by 64 canvas, `commit_frame` returned 1, `publishCpuCanvas` returned ok and made one `putImageData` call, and `drain_events` returned 64 bytes, that is 16 plus one 48-byte event. The header read pending 1, tail 0, capacity 256 and dropped 0. The event read kind 6, viewport 1, seq 0 and payload `[1, 64, 64, 0]`, which is generation 1, drawn extent 64 by 64 and flags 0, all derived from the call rather than copied from the implementation. Three hundred `publishCpuInteraction` calls then filled the ring. `drain_events` returned 12304 bytes, that is 16 plus 256 times 48. Pending was 256, dropped was 44, which is 300 minus 256, the first and last events were kind 6, seq ran 1 to 256 and the last payload flags read 8, the refining bit. `drainRing` over those bytes returned 256 events, dropped 44, kind 6 and 32-byte payloads. The observation rejects a ring that loses events, a stride or header that reads a neighbour event, a capacity that disagrees with the producer and a drop counter that does not count. It also rejects the remediation's own claim that the observation needs a browser.
- **AC8 was challenged by mutating the state wrapper's allocation.** `copy_state`'s `vec![0_u8; STATE_BYTES]` was changed to `STATE_BYTES - 4`. The boundary suite went red with 3 failures, including `expected null not to be null` at `readViewportState(wasm.copy_state())` and `expected 92 to be 96`. Reverting and rebuilding went green with 11 tests. This rejects a wrapper whose allocation does not track `STATE_BYTES`, and it shows that a stale literal 96 would be caught if `ViewportState` grew, because `write_state` would refuse and `copy_state` would return an empty vector.
- **The ring side of S1 was challenged by mutating the wrapper's stride factor.** `EVENT_STRIDE` in `drain_events` was replaced with the wrong literal `40_usize`. All 11 boundary tests stayed green. The full-ring probe went red with `full ring length = 0`, because `EventRing::copy_pending` refuses a buffer shorter than header plus pending times stride and `drain_events` then truncates to zero. This rejects the claim that the suite guards the wrapper's capacity and stride terms. It does not.
- **The derived stride was challenged against the HLD.** `EVENT_STRIDE` in `boundary.rs` was changed to `size_of::<RingEvent>() + 8`. `ring_layout_matches_hld_17_3` went red at `left: 56, right: 48`. Reverting went green. This rejects a stride that is not pinned to section 17.3's 48 bytes. The real constant cannot be mutated to a wrong value without breaking the producer's `copy_from_slice` of a 48-byte `RingEvent` into the slot, so the wrapper-tracking proof is the wrapper mutation above plus the source read that the factor is `EVENT_STRIDE`.
- **Composition and consumers.** `drain_events` now allocates `EVENT_HEADER_BYTES + RING_CAPACITY * EVENT_STRIDE`. Since `EventRing::push` refuses at `pending == RING_CAPACITY`, pending is at most capacity, so the allocation is at least header plus pending times stride for every reachable state. The short-buffer branch at `crates/ocelli-viewport/src/ring.rs:111` is therefore unreachable from this caller. The full-ring probe confirms the allocation is exactly sufficient, 12304 bytes against a required 12304.
- **AC2, AC3, AC5, AC6 and AC7 are unchanged material.** Their pass 1 mutations and built-module cases still describe this tree, because the untracked files and the generated file are byte-identical to pass 1's copies.

## Defects

### D1, the AC9 record still names a false blocker and leaves an achievable criterion unmet

**Where**: `.claude/scratch/F-104-progress.md:42`.

**What**: The record says "The presented-event half is **unmet in Node**", that `publishCpuCanvas` "needs an `OffscreenCanvas` and `ImageData`, which Node does not provide, so the integrated observation is a browser-only criterion", and "The AC's unmet state stands". The public-path and environment clauses are now correct. The conclusion is not. Node does not provide the globals, but a stub does, and the ring observation is made by the built module's own code, not by the test.

**Why it is wrong**: AC9 asks that `drainRing` on a copied ring written by the built module returns the presented event at the generated stride and the generated kind. I observed exactly that in Node. Only the DOM objects are stubbed. The session, the CPU raster draw, the owned frame buffer, `Session::present`, `EventRing::push_presented`, the ring copy and the copied bytes are the real Rust code in the built module. The stub `ImageData` carries a real `Uint8ClampedArray`, and `copy_presented` copies the presented frame into it through that array. `putImageData` is a no-op, so the browser blit itself is not observed, but AC9 does not measure the blit. A recorded reason that is false sends the next owner to a browser run that is not required, and it leaves a criterion unmet that this tree can evidence.

**Evidence**: `node f104-ac9-probe.mjs` against the dev module. `bindCpuCanvas(canvas, 64, 64, 1)` returned ok with device `[64, 64]`. `commit_frame(ticket, 4, 1, 1, 1, 1)` returned 1. `publishCpuCanvas()` returned ok with one blit. `drain_events()` returned 64 bytes with pending 1, kind 6, viewport 1, seq 0 and payload `[1, 64, 64, 0]`. After 300 `publishCpuInteraction()` calls, `drain_events()` returned 12304 bytes with pending 256, dropped 44, first and last kind 6, seq 1 and 256, and last payload flags 8. `drainRing` over those bytes returned 256 events with dropped 44. All 21 probe expectations were green, exit 0.

**Scope and regression**: The AC9 presented-event half is achievable now. The smallest meaningful regression is the boundary-suite case that publishes one frame through the stub canvas and drains it with `drainRing`, which is also the guard this pass's S1 needs. Owner: F-104 author. Add the case and mark AC9 evidenced, or state that it is achievable and not yet added. Do not record it as browser-only.

## Smells

### S1, the ring side of the derived wrapper has no executing guard

**Where**: `crates/ocelli-wasm/src/session.rs:1084` and `packages/core/src/boundary.wasm.test.ts:482`.

**What**: The remediation derives the ring allocation from `EVENT_HEADER_BYTES`, `RING_CAPACITY` and `EVENT_STRIDE`, so the duplicate is gone and the value is correct. The only test that reaches `drain_events` drains an empty ring, so the `capacity * EVENT_STRIDE` term is never exercised. The boundary suite asserts `ring.byteLength` equals `EVENT_HEADER_BYTES`, which looks like a ring guard and only covers the header.

**Failure mechanism**: Replacing `EVENT_STRIDE` with the wrong literal `40_usize` keeps all 11 boundary tests green and makes a full ring return 0 bytes, because `copy_pending` refuses the short buffer and `drain_events` truncates to zero. A future edit that hard-codes the pre-F-104 `16 + 256 * 48` would be green today and would silently lose the ring once `EVENT_STRIDE` grows past 48, which is the same failure pass 1's S1 named. The floor `test` gate does not compile the `cfg(target_arch = "wasm32")` module, and the boundary suite is manual, so nothing catches it.

**Why it is a smell**: The code is correct today and the hazard is specific. It is closed by the same boundary-suite case D1 asks for. One presented event makes the allocation load-bearing against a header-only literal. A filled ring makes the stride term load-bearing against any smaller literal.

## Nitpicks

`crates/ocelli-wasm/src/session.rs:1085` and `:1088` spell `ocelli_viewport::ring::RING_CAPACITY` and `ocelli_viewport::boundary::EVENT_HEADER_BYTES` and `EVENT_STRIDE` in full, while the same module imports `STATE_BYTES` and `StackViewport` with `use`. Preference only.
