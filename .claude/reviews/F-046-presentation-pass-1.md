## Defects

### D1, the window-domain test stays green if the function is discarded

**Where**: `crates/ocelli-viewport/tests/presentation.rs:216` and `crates/ocelli-viewport/src/presentation.rs:129`
**What**: `set_window_uses_the_voi_domain` checks width `0` and width `1` for `Linear` and `LinearExact`. It never reads `window()` back. Both functions refuse `0` and accept `1`, so the four asserts do not say which function was stored. Forcing `set_window` to ignore its `function` argument and call `replace_window` with `VoiFunction::Linear` left all 7 presentation tests green.
**Why it is wrong**: The plan says these checks are `VoiTransform::new`'s domain, not a new one. PS3.3 C.11.2.1.2 accepts LINEAR width at least 1. C.11.2.1.3.2 and C.11.2.1.3.1 accept any positive width. A width in `(0, 1)` is where they differ. HLD section 18 says this arithmetic exists once, in `ocelli-pixel`. A local rule that refuses every width below 1 would be a second domain, and this test would still pass. The product path does pass `function` into `VoiTransform::new` at `presentation.rs:177`. A throwaway probe, removed before this file was written, saw width `0.5` refused for `Linear` and accepted for `LinearExact` and `Sigmoid`, with the stored function equal to the one passed. The suite does not lock that. The same test would also stay green if a refusal wrote a new window and then returned `InvalidWindow`, because it never reads the chain.
**Evidence**: `bin/ocelli.sh test ocelli-viewport --test presentation -- --test-threads=1` exited 0 during that forced-`Linear` edit. After the edit was reverted, the same command exited 0 again. `rg` shows `set_window` calling `replace_window(center, width, function)` and `SoftTissue` width `400.0`.

## Nitpicks

### N1, `PresentationError::Unavailable` is the residual arm

**Where**: `crates/ocelli-viewport/src/presentation.rs:59`, and the `Err(_)` arms at lines 180 and 198
**What**: The plan names `Sequence` and `InvalidWindow`. `Unavailable` is every other `PixelError` from `VoiTransform::new` or `LutChain::new`. `LutChain::new` does not return `InvalidWindow`, so the `InvalidWindow` arm inside `rebuild` is not reachable.
**Why it does not block**: The call passes one centre, one width and index `0`, plus a range `output_range` already accepted when the chain was built. An honest photometric and an honest evidence value then make `LutChain::new` succeed. The extra variant is what keeps the match total without `unwrap` or `panic`. It is reached only when `Presentation::new` is given a photometric or an evidence value that did not build the chain. That is a broken constructor, not a window result the plan forgot to name.
