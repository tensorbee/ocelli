## Defects

### D1, an H.264 PPS is bound to whichever SPS is stored when it arrives, so two valid parameter set orders are refused

**Where**: crates/ocelli-codec/src/video/h264.rs:389 to :429 (`parse_pps` looks up `sps_table` at :396 to :406 and checks `pic_init_qp_minus26` against that SPS's bit depth at :427 to :429), called at :965.
**What**: the commit added a SPS lookup to `parse_pps` so that `pic_init_qp_minus26` can be checked against `-(26 + QpBdOffsetY)`. It refuses a PPS whose SPS has not yet arrived, and it checks the bound against the SPS stored at that moment rather than the one the PPS will activate. Both orders were accepted at 86857a8e.
**Why it is wrong**: Rec. ITU-T H.264 (08/2024) 7.4.1.2.1 activates a SPS when a PPS that names it is activated, and it activates the PPS when a slice refers to it. Each "shall be available to the decoding process prior to its activation". The same clause says that constraints on the relationship between SPS and PPS values "apply only to the active sequence parameter set and the active picture parameter set". 7.4.1.2.3 imposes no SPS before PPS order. So a PPS before its SPS conforms, and so does a PPS for the next coded video sequence sent ahead of that sequence's new SPS. The lead ruling on D1 asked for every value to be checked "against the range its clause gives", and 7.4.2.2's range is a relationship with the active SPS.
**Evidence**: `h264_gop12.h264` with its first SPS and PPS swapped, giving NAL types 6, 8, 7, 5 (`f241-p2-pps-first.h264`). Tip: `Malformed { structure: "H.264 picture parameter set", reason: "a picture parameter set refers to a sequence parameter set not yet seen" }`. Parent: OK, 60 frames. Second facet, `f241-p2-pps-new-sps.h264`: an 8-bit sequence, then a PPS with pic_init_qp_minus26 -38, then a 10-bit SPS with the same id, then an IDR. -38 is in range for the SPS it activates (QpBdOffsetY 12). Tip: `pic_init_qp_minus26 out of range`. Parent: OK, 4 frames. The same bytes with the SPS first are OK on both. ffmpeg decodes only 48 of the swapped clip's 60 frames, because its own PPS parse needs the SPS, so it is not the oracle here and the clause is.
**Scope and regression**: Annex B and TS H.264, on current HEAD, introduced by this commit. MP4 is unaffected because only the avcC SPS is parsed there. Smallest fix: drop the SPS lookup from `parse_pps`, read pic_init_qp_minus26 against the widest range, -62 to +25 (bit_depth_luma_minus8 is at most 6), keep the value in `Pps`, and check `-(26 + 6 * bit_depth_luma_minus8)` in `parse_slice` against the SPS the slice activates, where `first_mb_in_slice` and the reference limits are already checked. Regression tests: the two streams above, expecting 60 and 4 frames, and the second stream with an 8-bit SPS after the PPS, expecting the named refusal from the slice.

### D2, a level 8.5 HEVC SPS with more than 16 DPB pictures is refused as malformed, and the comment claiming the cap is false at that level

**Where**: crates/ocelli-codec/src/video/h265.rs:362 to :363 (`ue_max(MAX_DPB_SIZE - 1, "sps_max_dec_pic_buffering_minus1 over 15")`), comments at :24 and :358 to :359.
**What**: sps_max_dec_pic_buffering_minus1 is capped at 15 for every level. At general_level_idc 255 a value of 16 is refused as `Malformed`. The same commit exempts level 8.5 from the picture size limit at :328, so the two level rules disagree in one function.
**Why it is wrong**: H.265 (07/2024) 7.4.3.2.1 bounds the field by "MaxDpbSize - 1 ... where MaxDpbSize is as specified in clause A.4". A.4.2 opens the A-2 derivation with "When the specified level is not level 8.5", and A.4.1 says Table A.8 gives no limits for level 8.5, whose purpose is "to provide a suitable label for bitstreams that can exceed the limits of all other specified levels". So "A-2 caps MaxDpbSize at 16" is true for every level except 8.5, and a conforming level 8.5 stream is called malformed.
**Evidence**: `265_dpb16_l85.h265` (general_level_idc 255, sps_max_dec_pic_buffering_minus1 16, sps_max_num_reorder_pics 0): `Malformed { "HEVC sequence parameter set", "sps_max_dec_pic_buffering_minus1 over 15" }`. x265 `level-idc=8.5:ref=16:bframes=16` writes 15, so no encoder setting here produces the value. ffmpeg also refuses above 16.
**Scope and regression**: HEVC in every container, current HEAD, introduced by this commit. The practical reach is small, because browser decoders will not decode such a stream either. The defect is the false name, `Malformed`, and the false comment. Smallest fix: either lift the cap at level 8.5 as `side_limit` does, which keeps `num_negative_pics` bounded by the stream's own value, or refuse by name with `Unsupported { feature: "an HEVC decoded picture buffer over 16 pictures" }`. Then correct both comments. Regression test: the crafted SPS above at level 255 (accepted, or the named Unsupported) and the same SPS at level 186 (6.2), refused as now.

## Smells

### S1, the new range refusals have no boundary tests, so tightening a bound by one stays green

**Where**: the D1 bounds in h264.rs (:28, :34, :277, :429, :520, :628) and h265.rs (:28, :363, :406, :503, :203, :451), and the visual sample entry length check at mp4.rs:246.
**What**: apart from `delta_scale`, none of the new bounds has a test that writes the boundary value and one step past it. Of my 16 mutants that tighten a bound by one or narrow it, 12 survive: `MAX_FRAME_REF_IDX` 14, `MAX_DPB_FRAMES` 15, the H.264 crop window `+ 2`, idr_pic_id 255, the mmco5 delta_pic_order_cnt_bottom bound `2 - MaxPicOrderCntLsb`, `pic_init_qp_minus26` lower bound `-26` for every bit depth, HEVC `MAX_PIC_SIDE` 4 096, PCM depth `>=`, chroma_sample_loc_type 4, scaling_list_pred_matrix_id_delta 0 for sizeId 3, `MAX_DPB_SIZE - 2` and width a multiple of 2 * MinCbSizeY. The `D2-visual-entry` guard also survives removal, which turns its `Truncated { "MP4 visual sample entry" }` into `Malformed { "no avcC box" }` unnoticed.
**Failure mechanism**: each surviving mutant refuses valid streams that real encoders write. `-26` refuses every x264 10-bit stream at low QP (`h264_high10_cqp_lo` here writes -37), and 4 096 refuses every HEVC picture wider than 4K. D1 is the same class reaching HEAD: a refusal of valid input that the suite cannot see, because the committed clips stay inside the bounds and the crafted tests probe only `delta_scale`. The lead's D1 ruling made every one of these a refusal, so each is now a place where a later edit can quietly start refusing valid streams.
**Fix**: one table-driven unit test per parser in h264.rs and h265.rs, built with the existing `Writer`, that for each bounded field reads the boundary value and refuses the next value by its reason, with the clause cited per row. `f241-p2-craft.py` is a worked list of the rows and expectations, 146 cases. Add one fresh x264 10-bit low-QP clip to the generator so that the bit-depth-dependent bound is crossed by a real encoder's output. Add the truncated visual sample entry to `a_box_cut_short_is_refused_by_name`.

## Nitpicks

- N1, h265.rs:668. The HEVC 8-1 boundary `prev_lsb - lsb >= max_lsb / 2` survives mutation to `>` (`S1-265-8-1-ge`). The H.264 8-3 twin now has `poc_lsb_wrap_boundaries_of_8_3`, and pass 1 cleared 8.3.1 through a different mutant. A step of exactly MaxPicOrderCntLsb / 2 is a plausible hierarchical-B pattern at log2_max_pic_order_cnt_lsb 4, so a `PocState::next` case at exactly half would be cheap.
- N2, h265.rs:771 to :775 and video_demux.rs:1868. The layer clause added in 2f04797d is an equivalent mutant. `after_vcl` is cleared only at :732, next to `close`, which empties `picture` with `take()`. `picture` becomes `Some` only at a layer 0 slice, and that same slice sets `after_vcl` at :773. Adding `layer == 0` to :773 therefore changes nothing, and `a_layer_1_slice_stays_in_its_access_unit` passes either way. The test proves that a layer 1 slice does not open a picture, which is worth keeping. Its doc and the code comment cite NOTE 1 for a clause the result does not depend on, and the comment would be truer if it said so.
- N3, h264.rs:31 with :190 to :207, :530 to :552, and :234, :483 and h265.rs:345, :368. `se_range(-SE_LIMIT, SE_LIMIT, ..)` and `ue_max(u32::MAX - 1, ..)` can never refuse. `ue` stops at 31 leading zeros, so its largest value is 2^32 - 2, and `se` therefore spans exactly -(2^31 - 1) to 2^31 - 1. Measured: an se(v) of 2^31 and a ue(v) of 2^32 - 1 are refused as "an Exp-Golomb code longer than 32 bits", never by the named reason. The ranges are the clauses' own and the behaviour is right. Only the named reasons are unreachable. A comment saying the reader already enforces them would stop a later reader counting them as guards.
- N4, ts.rs:316 to :328. Ignoring a PAT or PMT with current_next_indicator 0 is right by H.222.0 2.4.4.5, and `a_table_not_yet_current_is_ignored` covers the case where no table is ever current. The adjacent case, a first table not yet current followed by a current one, now delays program acquisition. The video before the next current table is dropped, and the stream then opens mid-GOP and is refused by the existing rule against a slice before its parameter sets. `f241-p2-pat-next-first.m2t` and `f241-p2-pmt-next-first.m2t`: refused at the tip and accepted at the parent, 60 frames. The cause is the pre-existing no-skip policy that pass 1 cleared, so this is a consequence rather than a wrong check. It is recorded because the commit changed the outcome.
- N5, outside this range, from the fresh clips. For x264 `open-gop=1` and `intra-refresh=1`, MP4 marks decode indices 0, 9, 21 and 36 (or 0, 9 and 21) random access from `stss`, while TS and Annex B mark only the IDR at 0. ffprobe's TS key flags agree with the MP4 set. Starting only at an IDR is conservative and never wrong, but one stream gets two seek tables by container. Pass 1 cleared random access, and this range does not touch it.
