## Defects

### D1, every native-pixel image reports MULTIPLICITY on Pixel Data

**Where**: `crates/ocelli-dicom/src/conformance.rs:753` to `754` (`value_count` then `check_vm`) and `:808` to `813` (`value_count` falls back to `PrimitiveValue::multiplicity()`).
**What**: For a binary primitive, `value_count` returns the number of decoded elements, which is the byte count for OB and the word count for OW. That is not the Value Multiplicity. The VM table holds Pixel Data (OB or OW, 1), the six palette elements (the three data elements are OW, 1) and Extended Offset Table and its Lengths (OV, 1). So a 512 by 512 native CT reports `MULTIPLICITY` measured 262144, minimum 1, maximum 1 on (7FE0,0010). A native palette file also reports it on (0028,1201) to (0028,1203), and an Extended Offset Table with two frames reports measured 2 on (7FE0,0001) and (7FE0,0002).
**Why it is wrong**: PS3.5 6.4, quoted in the plan: "Data Elements with a VR of LT, OB, OD, OF, OL, OV, OW, SQ, ST, UN, UR or UT shall always have a Value Multiplicity of one." The plan's AC1 expects a valid image to have zero findings.
**Evidence**: scratch run over `corpus/data`. `real/ct_cmb_mml/00000012.dcm` (224 elements) has exactly one finding, `MULTIPLICITY` on PixelData measured 115600. Every `real/mr_eay131` file has the same finding measured 49152. The same happens on `real/dx_varepop`, `real/us_cmb_crc` and every native synthetic file. `synthetic/sc_palette_color.dcm` adds it on all three palette data elements. Encapsulated files do not show it, because `Value::PixelSequence` passes 1. My case `pixel_many` (8 bytes of OW) gives measured 4, and `eot_multi` gives measured 2 on both OV elements.
**Scope and regression**: present on the staged tree. Once the viewer half lands, the badge reads at least 1 on every uncompressed image, which defeats the story's purpose. The finding is false, and it sits in a report whose job is to be believed. AC1's fixture masks it because its Pixel Data is a single 2-byte word (`tests/conformance.rs:225`). Smallest regression: AC1 with Pixel Data of at least two words, plus a palette fixture with real-length data and an Extended Offset Table with two entries, each giving no MULTIPLICITY. The fix is to measure VM 1 for OB, OD, OF, OL, OV and OW, as already done for SQ and PixelSequence.

### D2, a legal padded last value of a multi-valued DA or DS is reported as a format violation

**Where**: `conformance.rs:1370` to `1372` (`valid_da` requires `raw.len() == 8`) and `:1582` to `1584` (`valid_ds` calls `parse_decimal_string`, whose `frame_geometry.rs` check `raw.len() > DECIMAL_STRING_MAX_BYTES` refuses 17 bytes).
**What**: `length_finding` correctly admits a last value that is one over the limit and ends in the pad (`exceeds`, `:1076`). The format check then gets the same raw text with the pad still on, and applies the length limit again. The AS, TM, DT, IS, UI and PN format checks strip or trim the pad first. DA and DS do not.
**Why it is wrong**: PS3.5 6.4: "a single padding character shall be applied to the end of the Value Field (to the last Value), in which case the length of the last Value may exceed the length of Value by 1." Plan decision 8 applies that exception to every VR.
**Evidence**: case `da_multi_pad`, (0018,1200) DA `20240101\20240102 `, gives `DA-FORMAT` value 2. Case `ds_last16_pad`, Pixel Spacing `0.50\0.48828125000000 `, gives `DS-FORMAT` value 2. Case `ds_iop16`, Image Orientation (Patient) as six 16-character values (101 bytes, padded to 102), gives `DS-FORMAT` value 6. The same 16-character DS as the first value (`ds_first16`) gives none.
**Scope and regression**: present on the staged tree. DS values written to fill 16 characters are common in real files, and IOP and IPP are multi-valued, so this produces false findings on otherwise valid images. Smallest regression: AC4's pattern repeated for DA and DS, a padded last value of exactly limit plus one, expecting no finding. Strip the one pad before calling `valid_da` and `parse_decimal_string`, and leave the length decision to `length_finding`.

### D3, the report echoes any text stored in SOP Class UID

**Where**: `conformance.rs:762` to `771` (`note_root_facts` stores the raw (0008,0016) text) and `:685` to `687` and `:1723` to `1732` (`ModuleScope::NotEvaluated { sop_class }` is written to `modules.sopClass`).
**What**: When (0008,0016) is not one of the four UIDs, the report repeats its first value as text, whatever it holds. With `SECRET^NAME` stored there, the JSON reads `"sopClass":"SECRET^NAME"`, and the same report flags that value as `UI-FORMAT`. The TS reader passes the string through (`conformance.ts`, `readModules`).
**Why it is wrong**: the plan's decision 5 says a report "never carries a value", and its API section allows exactly one exception: "A SOP Class UID is the only value the report repeats, because it is a registry identifier." A value that fails the PS3.5 9.1 grammar is not a registry identifier. It is arbitrary data, and it may identify a patient, which the privacy rule exists to stop.
**Evidence**: case `sop_name` gives `NE:'SECRET^NAME'` plus `UI-FORMAT` on (0008,0016). Case `sop_bad_uid` echoes `1.2.840.0123456`, which also fails 9.1. A grep for every other planted value over all case output finds nothing.
**Scope and regression**: present on the staged tree, and it reaches the viewer's module line once AC33 lands. AC25's test cannot see this, because no fixture puts a non-UID in (0008,0016). On top of that, the test removes `fixture.sop` from the JSON (`tests/conformance.rs:1734` to `1736`) and drops every secret that equals a registered SOP class (`:1740`). I judge the carve-out itself sound for the fixtures it runs: it removes only registered UIDs, `META_SECRETS` are not substrings of them, and a standalone `0.1` would still be caught. But it does not reach this leak. Smallest regression: a fixture with a non-UID SOP Class UID that is scanned like any other secret, with `sopClass` expected to be null, or to say only that the UID is invalid. Echo the SOP class only when it passes `valid_ui`.

### D4, ESC passes the LO, SH, PN, UC, ST, LT and UT repertoire when no ISO 2022 character set is declared

**Where**: `conformance.rs:1142` to `1144` (`extended_problem` returns `None` for U+001B unconditionally).
**What**: An LO holding ESC with (0008,0005) `ISO_IR 100`, or `ISO_IR 6`, gives no finding. Without (0008,0005) it gives `TYPE1C-ABSENT`, which is decision 6 and correct.
**Why it is wrong**: PS3.5 Table 6.2-1, quoted in the plan for LO, SH, PN and UC: "all Control Characters except ESC when used for [ISO/IEC 2022] escape sequences". For LT, ST and UT: "(and ESC when used for [ISO/IEC 2022] escape sequences)". When every declared term lacks the `ISO 2022` prefix, PS3.3 C.12.1.1.2 means no code extension is in use. An ESC cannot then be an escape sequence, and the condition can be decided from the data set.
**Evidence**: cases `esc_latin1` and `esc_default_cs` each give `[]`.
**Scope and regression**: present on the staged tree. This is a false negative on a rule the report says it checks, so it is less harmful than D1 to D3, but it is still a listed rule that is not enforced as stated. Smallest regression: a `fixture_control_characters` row, LO with ESC under `ISO_IR 100`, expecting `REPERTOIRE` class Control. If the lead prefers to keep ESC always allowed, the fix is to say so in the catalogue and the LLD rather than in the rule's section text.

## Smells

### S1, the "exceed by exactly one" boundary of the pad exception is untested

**Where**: `conformance.rs:1076`. **Mechanism**: I mutated `measured == limit.saturating_add(1)` to `measured <= limit.saturating_add(2)` and the whole conformance suite stayed green (29 passed). AC4 rejects "the exception for every value, or for none", but no fixture has a last value two over the limit that ends in a pad. The rule could widen silently. **Regression**: a last CS value of 18 bytes ending in a space, expecting VALUE-LENGTH Bytes 18 against 16.

### S2, the ISO_IR 192 byte-length branch is untested, and the implementer's AC15 line claims otherwise

**Where**: `conformance.rs:776` to `777` and `:1044` to `1052`. **Mechanism**: inverting `state.utf8 = code == "ISO_IR 192"` to `!=` leaves all 30 conformance and typegen tests green. The LO fixtures that carry ISO_IR 192 count characters and never read `utf8`. The flag only affects `measured_bytes` for DA, DS, DT, IS, TM, UI, UC and UT, and no fixture puts a non-ASCII character in one of those under ISO_IR 192. The implementer's report says "AC15. `fixture_character_set`. Only an exact trimmed `ISO_IR 192` at root `(0008,0005)` selects UTF-8 byte length." The suite does not prove that. If the claim is copied into the progress note or AS_BUILT, it becomes false tracked prose. **Regression**: a byte-limited VR with a multibyte character under ISO_IR 192 against the same bytes without it, expecting different measures, or delete the flag if the lead decides it carries no observable rule.

## Nitpicks

- N1. `scope_sentence_is_exact` (`tests/conformance.rs:1855`) compares the JSON with the `CONFORMANCE_SCOPE` constant, so editing the constant leaves it green. The typegen test and the TS literal assertion catch the edit, so nothing is lost. The Rust test could pin the literal instead.
- N2. No fixture puts two findings on the same path, tag and value, so reversing the rule tiebreak in the sort (`:550`) stays green. Output is still deterministic. The documented order "path, tag, value, rule" is only proved for its first three keys.
- N3. `readConformanceReport` refuses a path item of 0 (`isPositiveU32`), but mutating it to `isU32` leaves the TS suite green.
- N4. A report with no `scope` field is refused as `shape`, not `scope` (`conformance.ts`, the first `isRecord` guard). Plan decision 13 reads "refuses a report without the exact sentence". The refusal happens either way. Only the reason differs.
- N5. Unconfirmed concern. A Type 1 string of only spaces, such as Modality `  `, satisfies presence (case `modality_spaces` gives none). PS3.5 says spaces are not significant for CS. Whether a value that is all padding is "empty" under 7.4.1 is not settled by the quoted text.
- N6. Unconfirmed concern. Without (0008,0005), C1 controls (bytes 80H to 9FH) decode to U+0080 to U+009F. `extended_problem` returns early for anything above U+007F, so they count as an extended repertoire rather than as control characters (case `lo_c1`).
- N7. `CHARSET-UNDECLARED` and `BINARY-LENGTH` are in the wire `rules` list, and the checker never emits either. The first is reported as `TYPE1C-ABSENT`. The second cannot be reached through dicom-parser 0.10.0. The doc comments say so. A viewer listing "the rules it lists" will still show two rows that cannot fire.
- N8. The implementer's AC labels do not match the plan's inventory. For example, the report's AC5 is the plan's AC17 and its AC15 is the plan's AC16. Renumber before the labels reach a tracked progress note.
- N9. `lib.rs` puts the F-225 line between the F-016 and F-017 lines of a list that is otherwise in story order.

## Verified clean

- PS3.5 Table 6.2-1 limits. LO 64, SH 16, ST 1024, LT 10240 and PN 64 per group are counted in characters. AE 16, CS 16, DS 16, IS 12, TM 14, DT 26, UI 64, UC, UR and UT 2^32-2 are counted in bytes. AS 4 and DA 8 are fixed. The character-limited set matches the 6.1.2.2 list, with UC and UT byte-limited as the table says.
- Per-VR repertoire. CS takes uppercase, digits, space and underscore. AE excludes backslash and controls. AS takes digits and D, W, M, Y. DA takes digits. TM takes digits, `.` and space. DT takes digits, `+`, `-`, `.` and space. UR takes the RFC 3986 set, with a space only as trailing padding. LT, ST and UT allow TAB, LF, CR and FF, and LO, SH, UC and PN do not. Backslash is allowed only in LT, ST and UT, matching dicom-parser 0.10.0, which reads UT, ST, UR and LT unsplit (`stateful/decode.rs:1052`). DEL is a control.
- Formats. AS is nnn plus a unit letter. DA follows the Gregorian rule: 1900-02-29 is invalid, 2000-02-29 and 2024-02-29 are valid, the leap rule mutation was seen red in the implementer's run, and month and day bounds hold. TM accepts HH, HHMM and HHMMSS with a 1 to 6 digit fraction only after SS, rejects 2400, accepts second 60, and rejects a lone `.`. DT accepts body lengths 4 to 14, a fraction only after 14 digits, and an offset of exactly four digits from -1200 to +1400 with minutes at most 59, and refuses -0000. IS is 32-bit, signs and padding are allowed, embedded spaces are not. DS reuses `parse_decimal_string`, with `1E999` as DS-RANGE. UI follows 9.1 for components and leading zeros, and refuses a NULL anywhere except the pad and a space pad. PN allows at most 4 carets per group and 3 groups.
- VM table. All 47 rows match the plan's PS3.6 transcription, including Patient Orientation 2, Pixel Spacing 2, IOP 6, IPP 3, the palette descriptors 3, and Specific Character Set 1-n. The cross-check against the dictionary passes.
- Presence. The Type 1 and Type 2 lists for the seven modules, and their split by IOD, match the plan's PS3.3 tables: CR has six modules, CT, MR and PET seven. Patient Position 2C applies to CT and MR only. Patient Orientation 2C applies to CR only. Planar Configuration requires SPP > 1. All six palette elements are required for PALETTE COLOR. Pixel Data is required unless a non-empty Provider URL is present. Extended Offset Table requires its Lengths. Specific Character Set 1C fires once. Other SOP classes are `evaluated: false`, have no `notChecked` and no presence finding, and their value rules still run.
- No `unsafe`, no `wasm-bindgen`, no new dependency. `parse.rs`, `frame_open.rs` and the viewer files are untouched. `check_conformance` takes `&ParsedDicom`. No arm panics: every `as` is `try_from` with a saturating fallback, and slicing goes through `get` or `char_indices`.
- Determinism over 155 real and derived reports. Key order matches the plan. Tags are uppercase hex.
- Typegen drift goes red when a rule id is renamed. The three new value exports are in `PUBLISHED`, and the type exports are type-only.
- The implementer's "Tree versus plan" substitutions. `ABC\DE` still tests 2 values against VM 1. `12.5` still tests a fraction without SS. The three-value charset without a trailing space still tests 1-n. The 65-character LO rows, 66 characters ASCII and 65 characters in 66 bytes under ISO_IR 192, still test character counting and the single-value limit. The 17-byte DS, the 13-byte IS and the 65-byte UI as the first of two values still test the length rule with a parseable even length. BINARY-LENGTH being unreachable is measured, which decision 12 allowed. The privacy carve-out is judged under D3.
