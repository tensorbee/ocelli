## New smells

### S1, `ToolchainPins` asserts the values of whatever CI happens to pin, not that the digest-moving tools are pinned at all

**Where**: `scripts/tests/test_corpus_synth.py:542-563`, against
`.github/workflows/ci.yml:119-148`.

```python
        pinned = dict(re.findall(r'"([A-Za-z0-9_-]+)==([0-9][0-9A-Za-z.]*)"',
                                 self.workflow()))
        self.assertIn("pydicom", pinned, "the CI pin block moved or changed shape")
        shared = set(pinned) & set(corpus_synth.BUILT_WITH)
        self.assertTrue(shared)
```

**What**: `shared` is an intersection, so a package that stops being pinned
simply leaves the set and is no longer compared. Only `pydicom` is asserted to
be present at all. The class docstring says the test is "the only remaining way
this pair can drift without something noticing", and `ci.yml:121` says "Every
Python package below is pinned and so is OpenJPH". A dropped pin is drift, it
makes that comment false, and nothing notices.

The DCMTK assertion has the same shape one level down. `assertNotIn("dcmtk==",
...)` checks a pip spelling, and the step it is about is `apt-get install -y
dcmtk`, where a pin is written with one equals sign.

**Why it is a smell and not a defect**: every pin agrees with `BUILT_WITH`
today, all four shared entries included, and I checked the OpenJPH tag and the
DCMTK step by hand as well. Nothing is currently wrong. What is absent is the
part of the guard that would keep it that way.

**Why it is worth a finding rather than a nitpick**: this class was added in
this round for exactly one purpose, and the two mutations most likely to happen
in that file, someone removing a pin and someone pinning DCMTK, both pass.

**Evidence**:

```text
MU4   ci.yml "pylibjpeg-openjpeg==2.5.0"  ->  "pylibjpeg-openjpeg"
      Ran 3 tests ... OK                                  <- GREEN
MU4b  ci.yml "pyjpegls==1.5.1"            ->  "pyjpegls"
      Ran 3 tests ... OK                                  <- GREEN
MU7   ci.yml apt-get install -y dcmtk     ->  ... dcmtk=3.6.7-9.1build4
      Ran 3 tests ... OK                                  <- GREEN
```

`3.6.7-9.1build4` is the real Ubuntu 24.04 version, taken from
`packages.ubuntu.com/noble/dcmtk`, so MU7 is the pin someone would actually
write. The same hole runs the other way: a new digest-moving entry added to
`BUILT_WITH` and forgotten in CI leaves `shared` short and the test green.

**Fix**: assert the membership as well as the values, for instance by naming
the four shared keys the test expects to find and comparing that set to
`shared`, and by asserting on `re.search(r"dcmtk[=\s]", ...)` or on the exact
install line rather than on `dcmtk==`. Two lines.
