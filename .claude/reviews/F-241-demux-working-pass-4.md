## Smells

### S1, two B-only reads in `parse_slice` are needed by no row, so removing either stays green

**Where**: crates/ocelli-codec/src/video/h264.rs:592 to :594 (the second `skip_list_modification`) and :602 (`(slice_type == B).then_some(l1)`). The builder at h264.rs:1722 to :1724 writes ref_pic_list_modification_flag_l1 as 0 always, and its comment at :1725 says no PPS sets weighted_bipred_idc 1.
**What**: the B slice this range adds exercises the l1 override and nothing after it. Mutant `P4-no-l1-modification` deletes the second list modification read, and mutant `P4-no-l1-weights` passes `None` for list 1's weights. Both survive the lib tests and video_demux. The crafted B slice is non-reference, so nothing past the list modification is read, and no tracked clip has a B slice whose later fields depend on either read.
**Why it matters**: 7.3.3 puts ref_pic_list_modification( ) with its l1 half (7.3.3.1, slice_type % 5 = = 1) and pred_weight_table( ) with its l1 loop (7.3.3.2) before dec_ref_pic_marking( ). A parser that drops either read misaligns a reference B slice's dec_ref_pic_marking. An x264 b-pyramid stream has reference B slices. A misread or missed memory_management_control_operation 5 changes the POC under 8.2.1 and so the display order, with no error. The l1 modification also carries abs_diff_pic_num_minus1's bound, 0 to MaxPicNum - 1 under 7.4.3.1, which has rows for list 0 only. The lead's S1 ruling for pass 2 asks for every range bound at the bound and one past it.
**Evidence**: `f241-p4-mutate.log`, both `SURVIVED`. The fix below was applied in a scratch export. It is green as written and red under `P4-no-l1-modification`.
**Fix**: give `Craft` a list 1 modification. In a scratch export, `modification_l1: Option<u64>` writing `flag(true).ue(0).ue(d).ue(3)` in place of the fixed `flag(false)`, plus rows "l1 abs_diff 15" (accepted) and "l1 abs_diff 16" (refused, "picture number difference"), kills `P4-no-l1-modification`. For the weights, let the PPS builder set weighted_bipred_idc 1 for a B row, write an l1 weight past the bound (128 or -129, 7.4.3.2), and expect "prediction weight". That row needs pred_weight_table's l1 loop in the builder, written from 7.3.3.2.
**Scope and regression**: present at c5b6c6f1. No verdict on any stream changes today. Consumers are `h264::access_units` and through it every container route. The smallest regressions are the two rows above.
