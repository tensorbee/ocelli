## Defects

### D1, a box that runs past the end of the input is accepted, so trailing bytes and truncated boxes decode, and the module doc says they are refused
**Where**: `crates/ocelli-codec/src/jpegxl_icc.rs:206` to `:211` (the truncation), `:62` to `:65` (the claim)
**What**: `walk_container` takes a box whose declared size is larger than the remaining input and silently shortens it to the input (`.min(available)`). Any eight or more bytes after the last box therefore read as one more box of an unknown type, are skipped, and leave no tail. Measured on this tree: the RGB8 codestream in `sig + ftyp + jxlc` followed by the nine bytes `01` to `09` returns `Ok(())` and the reference. The same with three bytes refuses `TrailingData`. The tracked `jpegxl_container.jxl` and `jpegxl_recompression.jxl` with 40 bytes of `0x42` appended return `Ok(())`, and with 1 or 7 bytes refuse `TrailingData`. A `jxlc` box declaring 1,000 more bytes than present and a `jxlc` followed by an `Exif` box declaring 1,000 more bytes than present both decode to the reference. The module doc says "Bytes of a container after the last complete box are not part of the codestream and are refused as [`CodecError::TrailingData`] after the decode".
**Why it is wrong**: microscope section 3, the sentence is false for every tail of eight bytes or more. ISO/IEC 18181-2 (and ISO/IEC 14496-12, whose box syntax it uses) defines the size as the length of the whole box, so a size larger than what remains is a truncated or malformed file. The amendment's purpose for this hand-written walk is that malformed containers are refused rather than interpreted, and the design's trailing rule (decision 6) is "anything else is `TrailingData` when detectable". Here the bytes are detectable, because the walker knows exactly where the input ends.
**Evidence**: `p4_containers` cases `jxlc + 9 junk bytes`, `jxlc + 3 junk bytes`, `jxlc declares +1000`, `jxlc + Exif declares +1000 (truncated)`, and `p4_trailing_every_fixture` for the two tracked containers.
**Scope and regression**: the same inputs give the same results on `f1a5e51`, where `jxl-oxide`'s container parser streamed the partial box. So the behaviour predates this round, but this round wrote the walker that now decides it, chose the truncation in its comment at `:208`, and wrote the false sentence. No pixel is wrong, because a truncated codestream box still fails the decode when the frame is incomplete. The smallest remedy is to refuse a box whose declared size exceeds the remaining input with `InvalidCodestream`, which also keeps pass 2 D2's 46 byte case refused. If the lead prefers the lenient reading, the sentence must be narrowed to tails shorter than a box header. Regression: the nine-byte tail and the `Exif` box that runs past the input, each expecting a refusal.

### D2, the extra-channel test cannot see the pre-check refusal it claims to guard, and its comment says it can
**Where**: `crates/ocelli-codec/tests/jpegxl.rs:1112` to `:1135` (`extra_channel_header_refuses_before_the_reparse`), the comment at `:1118` to `:1121`, and the refusal at `crates/ocelli-codec/src/jpegxl_icc.rs:335`
**What**: the comment says "removing the refusal turns this red through time and not through kind". Mutation M1 deletes `|| !header.metadata.ec_info.is_empty()` from `probe` and leaves every `jpegxl` test green, this one included, in 0.01 s. `read_header` now grows its window geometrically, so the 256 channel header reaches `validate_header`, which refuses it with the same `UnsupportedPixelFormat` in milliseconds. Mutation M2 (one byte at a time again in `read_header`, pre-check intact) is also green. The implementer's receipt, red at 179.6 s, was taken with both changes reverted together, which is the only combination the test detects.
**Why it is wrong**: microscope section 2, a test that passes both ways for the change it is named after, and section 3, a false sentence about what the test detects. The lead's amendment makes the pre-check refusal a requirement in its own right, and nothing executes its removal.
**Evidence**: `mut.py` M1 and M2, `test result: ok. 22 passed` for each.
**Scope and regression**: test and comment only. The refusal itself is correct. `validate_header` checks bits per sample (`FrameMismatch`) before extra channels, so the same header against a descriptor with a different Bits Stored separates the two: the pre-check gives `UnsupportedPixelFormat` and M1 gives `FrameMismatch`. A unit test calling `prepare` directly also works. Either replaces the time bound as the guard, and the comment should then say what it detects. No input I found makes M2 measurably worse (an extension skip parses in constant time), so the `read_header` growth needs no time test. It needs only no claim that one exists.

**Where**: `crates/ocelli-codec/src/jpegxl_icc.rs:221` (jxlc after jxlp), `:230` (jxlp after jxlc), `:234` (jxlp after the final one), `:248` (index order), tested by `containers_that_break_the_extraction_rules_refuse` (`tests/jpegxl.rs:793`)

**Mechanism**: this is pass 3 S1's class again, rules present and unexecuted. The next edit to this hand-written walk (D1 asks for one) can drop an ordering rule and accept a container that `jxl-oxide`'s own parser refuses, with nothing going red.

## Nitpicks

- **N1.** The walker does not refuse a container that 18181-2 calls malformed when the malformation sits in a box it skips. `ftyp` missing, misbranded or out of place, `jxll` after the codestream, a `brob` box shorter than its 4 byte inner type, and a `brob` naming `jxlc`, `jxlp`, `brob` or `jbrd` all decode. `jxl-oxide` refuses the last two (`parse.rs`), and `f1a5e51` refused the `brob jxlc` case. No pixel depends on them. The lead may want them listed in the module doc's rule list or refused.
- **N2.** `cargo doc --document-private-items` fails on three intra-doc links this round added: `UninitializedJxlImage::feed_bytes` (`jpegxl.rs:272`), `crate::jpegxl::validate_header` (`jpegxl_icc.rs:6`) and `crate::jpegxl::JpegXlDecoder::decode` (`jpegxl_icc.rs:26`, a trait method). No gate builds private docs.
- **N3.** "The header probes allocate nothing" (`jpegxl_icc.rs:47`) is true only without extra channels. `prepare` on the 256 channel header allocated 290,560 bytes at peak against a 274,823 byte input. The next sentence gives the bound, so the first should say "nothing beyond the bound below".
- **N4.** `jpegxl.rs`'s module doc says "Two bounds sit outside the tracker". `UninitializedJxlImage::feed_bytes` copies the fed window into its own `Vec`, which is input-bounded, and the TOC vectors are capped at 65,536 entries. Both predate this round and are bounded, but the count is not the full list. `read_header`'s "the number of codestream bytes `feed_bytes` consumed to reach a header" is now the whole first window, frame bytes included. "Which is where `load_rest` resumes" is the true half.

## Limitations and handoff

It is detectable in principle from the frame TOC sizes. That is the lead's call and does not block this pass.
