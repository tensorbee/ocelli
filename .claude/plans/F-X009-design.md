## What the specification does not cover

The HLD has no section on repository guards at all. Section 27 gives seven
rules and says what a human must check, `docs/hld/12-workspace-and-build.md`
gives the build, and section 11 gives the oracle. Nothing anywhere in
`docs/hld/` describes `scripts/`, `.githooks/`, `bin/ocelli.sh` or the gate
profiles, because those are this repository's machinery for holding the
specification rather than part of it. So every decision below is this plan's
and none of it is transcribed. Listed explicitly, because an empty section and
a section nobody wrote look identical.

1. **That a guard needs a test at all.** 27.3 makes the mutate-and-watch step a
   human's, once, at review time. Making it standing is this repository's
   addition and F-010 measured why it is needed.
2. **Where the probe runs.** The HLD says nothing about isolation, so the
   disposable-repository design, the git choke point, the environment scrub and
   the tripwire are all this plan's.
3. **The catalogue format and its location.** Modelled on
   `tools/oracle/src/faults.mjs` by analogy, not by instruction.
4. **The profile split.** `--floor`, `--sprint` and `--all` are
   `.claude/WORKFLOW.md`'s, not the HLD's. Which probe lands in which is a cost
   decision this plan makes and justifies.
5. **The completeness argument.** Nothing normative says how to prove a census
   covers everything. The discovery scan, the bidirectional claim matching and
   the declared-constant ratchet are this plan's answer.
6. **What "the specification" means for a guard.** R2 says tests derive from
   the spec. For `crates/ocelli-pixel` the spec is a DICOM section. For
   `scripts/unsafe_allowlist_check.py` the spec is HLD 27.2 R5, and this plan
   has to say so explicitly because the alternative reading, that the guard's
   source is its own specification, produces a test that passes forever.
7. **The scope boundary.** Whether a runtime refusal inside a crate counts as a
   guard. This plan says no and says where the line is.

## Approach

### 0. The shape of the answer, in five sentences

One **catalogue** declares every refusal this repository can produce, with the
normative citation that says what the refusal is for, a recipe for the state
that should trigger it, and a fragment of the message it should produce. One
**runner** drives each recipe into a disposable git repository under `$TMPDIR`,
requires the guard to refuse, requires a control run on the unmutated copy to
pass, and reports a probe that did not refuse as a failure of the harness. One
**census** proves the catalogue is complete by discovering refusal sites
statically and refusing any site no entry claims and any entry no site backs.
Two gates carry it, `guards` in the floor for everything that needs no
toolchain and `guards-deep` in the sprint and release profiles for everything
that does. The oracle's existing fault catalogue is **adopted rather than
copied**, because a second declaration of the same twelve faults is the same
defect as a second copy of the LUT chain.

### 1. What counts as a guard, and where the boundary is

**In scope: a refusal that protects the repository or the process.** Everything
`bin/ocelli.sh gate` invokes, every executable under `.githooks/`, every
refusal inside `scripts/`, `ci/` and `tools/oracle/`, and the lint and manifest
configuration that decides what those refusals cover.

**Out of scope: a refusal inside a crate at runtime.** F-004's "reports
unavailable rather than quietly differing" and F-005's panic mapping are
refusals, and they need tests that watch them fail, but those tests belong to
those stories and live beside the code as unit and property tests. Pulling
them in here would make the story unbounded and would put a second owner on
files those stories are writing. The census's discovery scan is therefore
rooted at `scripts/`, `ci/`, `.githooks/`, `bin/` and `tools/`, and explicitly
not at `crates/`.

**The one crossing.** `crates/ocelli-core/tests/ui/` and
`crates/ocelli-compute/tests/ui/` are compile-fail cases under `trybuild`, and
they are already standing guard tests of exactly the kind this story wants: a
case that starts compiling fails `cargo test`. The census records them as
covered by an existing standing test and adds nothing. Naming them matters,
because the alternative is a census that reports the device-ownership contract
uncovered when its strongest half has been watched on every run since F-008.

### 2. The catalogue, `scripts/guards/catalogue.py`

Production data, not test data, for the reason `docs/lld/oracle.md` gives about
`src/faults.mjs`: several entries carry the bytes or the manifest fragment the
probe writes, so they are inputs to a mechanism rather than assertions about
one. Python rather than JSON so an entry can carry a callable that builds a
fixture, and rather than Markdown because a Markdown catalogue under
`.claude/` or `docs/` would itself be scanned by `prose_check.py` and by
`deviation_check.py`, and several entries have to contain the exact text those
guards refuse.

Each entry declares:

| Field | What it carries |
|-------|-----------------|
| `id` | Stable dotted name, `content.dicom-magic`, `ledger.trailer-tree-mismatch` |
| `guard` | The gate name and the file the refusal lives in |
| `spec` | The normative citation: an HLD section, a `D-NN` row, a `CLAUDE.md` hard rule, or a `.claude/WORKFLOW.md` rule |
| `refuses` | One sentence, written from `spec`, saying what must be refused |
| `probe` | How to build the rejected state. A callable over a sandbox handle |
| `invoke` | How the guard is run: a module-level function for a level-1 probe, or an argv for a level-3 subprocess |
| `expect` | A fragment of the specific message the refusal produces |
| `needs` | `none`, `cargo`, `npm`, `wasm-pack`, `browser`, `corpus`, `gpu` |
| `profile` | `floor` or `deep`, derived from `needs` and checked against it |
| `covered_by` | For a refusal already watched elsewhere, the standing test that watches it |

`spec` and `refuses` are what make this satisfy R2 and they are the two fields
a reviewer should read first. The probe is derived from the `refuses` sentence,
which is derived from the citation. It is **not** derived from the guard's
source, and the worked examples in section 6 below show the difference, because
this is the one place the story can quietly fail while looking finished.

`expect` is allowed to be the implementation's own text, and that is not a
contradiction. Its job is narrow: prove the run went red **for the declared
reason** rather than by accident. `tools/oracle/src/faults.mjs` states the
argument for the `truncate` fault, that a `decoded:` prefix "would be satisfied
by a corrupted corpus row or a codec regression just as happily", and the same
holds here. A guard whose message is reworded then turns the harness red, and
the author has to re-read what the guard is for before they can make it green.
That is a feature. The R2 risk lives in the probe's **input**, and that is the
field a review should interrogate.

### 3. Driving a guard red without touching the developer's tree

This is the part that has to be right, because a guard test that leaves a
staged DICOM behind or a corrupted index is worse than the defect it prevents.

**The sandbox is a fresh git repository under `$TMPDIR`, not a worktree.**
`docs/runbooks/guard-verification.md` uses `git worktree add --detach`, and
that is right for a human doing this once. It is wrong for a standing harness,
for two reasons the runbook itself records: a worktree is a full checkout, so
"every path-scanning guard otherwise sees a second copy of the whole
repository", and `git worktree add` writes into the developer's `.git`. The
harness builds instead:

```text
1. tmp = tempfile.mkdtemp(prefix="ocelli-guard-")
2. for each path in `git -C REPO_ROOT ls-files -z`, copy the WORKING TREE
   content of that path into tmp, preserving the mode bit
3. in tmp: git init -q, git add -A, git commit -q -m base
4. every git call runs with a scrubbed environment (see below)
```

**Working-tree content of `git ls-files`, and not `HEAD`, deliberately.** A
developer editing a guard has to see their edit probed before they commit, and
building from `HEAD` would probe the previous version and report success, which
is `AGENTS.md`'s "stage before you gate" lesson arriving from the other side.
Using `ls-files` rather than a directory walk also excludes `corpus/data`,
`node_modules`, `target`, `tools/oracle/out` and `.claude/verify-ledger.json`
by construction, so no patient data, no rendered reference frame and no local
evidence file is ever copied anywhere. It also avoids `git write-tree`, which
would write objects into the developer's object database.

**One choke point, and it refuses to run inside the repository.**
`scripts/guards/sandbox.py` exposes a single `git(*args)` and every call goes
through it. It refuses when the resolved cwd is inside `REPO_ROOT`, refuses
when the cwd is not the sandbox it was constructed with, and runs with:

- every inherited `GIT_*` variable removed from the child environment, so an
  exported `GIT_INDEX_FILE` or `GIT_DIR` cannot redirect a write into the
  developer's index
- `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` pointed at `/dev/null`, so the
  developer's global config, aliases and hooks path cannot reach the sandbox
- `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL` and the committer pair set to fixed
  harness values, so a commit works on a machine with no identity configured
  and never attributes a probe commit to the developer
- `GIT_TERMINAL_PROMPT=0`

The read-only calls against the real repository, `ls-files` and the tripwire's
status reads, are the only ones that name `REPO_ROOT`, they live in two named
functions, and they are the two functions a reviewer has to read.

**Reset between probes, with the pair the runbook warns about banned.** Inside
the sandbox, `git reset --hard` then `git clean -fdx`. The runbook records the
trap in terms: `git rm --cached <path>` followed by `git checkout -- <path>`
leaves the working tree broken and the path untracked, so "the very check you
are probing then skips it and reports clean. That is a false green produced by
the cleanup rather than by the guard." The harness never uses that pair, and
the census carries an entry for the harness's own reset so the ban is watched
rather than remembered.

**Cleanup when a probe fails halfway.** Four layers, and the design assumes
each will fail eventually:

1. The sandbox is created and removed in a `try` and `finally`, which is what
   `tools/oracle/tests/faults.mjs` already does with its `mkdtemp` and its
   `rm(..., {recursive: true, force: true})`.
2. `SIGINT` and `SIGTERM` handlers remove it and re-raise, so a developer's
   interrupt does not orphan a directory.
3. On start, the runner sweeps `$TMPDIR` for `ocelli-guard-*` directories older
   than one hour and removes them, so a `kill -9` leaves at most one orphan
   until the next run.
4. Nothing is ever written inside `REPO_ROOT`, so there is no residue to clean
   there. **A staged DICOM in the developer's index is impossible by
   construction rather than by cleanup**, which is the only version of that
   guarantee worth having.

**The tripwire.** Before the first probe the runner captures, from the real
repository: `rev-parse HEAD`, `diff --name-status`, `diff --cached
--name-status`, `ls-files --others --exclude-standard`, and `config --get
core.hooksPath`. After the last probe it captures them again and fails the
harness, naming the difference, if any changed. That turns "the harness left
residue" from an invisible defect into a red gate. It is content-level and not
stat-level on purpose, because `git status` legitimately refreshes the index's
stat cache and a tripwire that fired on that would be tuned away within a week.

**The DICOM fixture is synthesised and is not a corpus row.** 128 zero bytes
followed by `DICM`, built in memory. `scripts/staged_content_check.py` refuses
on the magic at offset 128, so 132 bytes exercises the refusal exactly.
Using a real corpus row would put patient data in a temporary directory for no
gain, and the corpus is absent in CI anyway.

**The three probe levels, and why level 3 is not optional.**

| Level | What it does | What it proves | What it cannot prove |
|-------|--------------|----------------|----------------------|
| 1, in-process | Call the detection function with an in-memory input | The detection logic itself | That anything calls it, or calls it over the right file set |
| 2, sandbox state | Build the rejected state in the sandbox | The state is buildable and realistic | Nothing on its own, it is level 3's setup |
| 3, subprocess | Run the guard's real argv with the sandbox as cwd | The wiring, the argv handling, the exit status the gate runner reads | Cheapness |

Level 1 alone is the failure mode the runbook's probe 18 describes: "not one
that fails wrongly, but one that has nothing to check and says so by
succeeding". So **every entry gets a level-3 run in some profile.** The profile
split in section 5 decides which one, and no entry is ever covered by level 1
alone.

**Hook probes become possible for the first time.** `.githooks/*` do nothing
until a clone sets `core.hooksPath`, which is per clone and untracked, and no
gate can safely fire them in the developer's repository. In the sandbox the
harness sets `core.hooksPath .githooks` and runs a real `git commit`, so the
pre-commit refusal, the commit-msg trailer emission, the commit-msg refusal of
a hand-written trailer and the pre-push refusal all become executable rather
than described. That is the single largest coverage gain in the story and it is
the strongest argument for the disposable-repository design over any in-process
alternative.

### 4. The recursion, answered rather than left hanging

The harness is a guard, so what watches it. Five mechanisms, in the order they
fire, and then the honest limit.

**a. Inverted success.** A probe whose guard exits 0 is a **failure of the
harness**, with the message `tools/oracle/tests/faults.mjs` already uses: the
guard it aims at did not fire, so it is a guard nobody has watched fail. A
probe builder that silently stops mutating anything therefore turns the gate
red instead of green. This inverts the usual risk: the broken-harness case is
loud rather than quiet.

**b. The mandatory control run.** For each guard file, the runner also runs it
against the **unmutated** sandbox and requires exit 0. This is not decoration.
It is precisely the thing whose absence made F-010's round 12 worthless: "its
own mutation harness was broken, so every earlier all-refusals-red result had a
red baseline and proved nothing". The control does a second job as well, which
is proving the sandbox is a faithful copy of the repository, because a guard
that goes red on an unmutated copy means the copy is wrong. And it does a
third, which the runbook names: "a guard that fails on everything is as useless
as one that fails on nothing". The control is run once per guard file rather
than once per entry, since the unmutated state is shared.

**c. The harness's own self test.** `scripts/guard_probe.py --self-test`,
following `tools/oracle/check_sidecars.py --self-test`, which exists for the
same reason: its helpers "only ever run on a mismatch", which no gate run
produces. The self test covers:

- the git choke point refusing a cwd inside `REPO_ROOT`
- the environment scrub actually removing an inherited `GIT_DIR`
- the tripwire detecting a planted change
- an `--only` filter naming an unknown id refusing, rather than reporting
  "every one caught" having caught none, which is the refusal
  `tests/faults.mjs` already carries
- a run in which zero probes executed refusing, which is
  `scripts/corpus_tests.py`'s "zero tests ran, which is not a pass"
- the reset function refusing the `rm --cached` and `checkout --` pair

**d. The census watches the catalogue, and the harness watches the census.**
`scripts/guard_census.py` is itself a guard with refusals, and those refusals
are catalogue entries with probes, driven by the same runner. So the two
components watch each other rather than each watching itself.

**e. CI runs the `guards` gate, and `scripts/ci_floor_check.py` refuses a floor
gate CI does not invoke.** That chain already exists and this story joins it
rather than building a parallel one.

**The honest limit, stated rather than glossed.** The regress terminates at one
runner whose own refusals are self-tested and whose control run is mandatory. A
human still has to read that runner once. What the story buys is that the thing
a human must read carefully shrinks from twenty-six scattered scripts to one
small file, and that everything above it is machine-checked. Claiming a closed
loop would be the exact overclaim this repository exists to refuse, and
decision D14's posture in `docs/hld/11-decision-log.md`, measured rather than
absolute, is the right one here too.

### 5. Cost, and what runs where

**The constraint.** `--floor` is what CI runs on every push, and the story is
worthless if its coverage only runs when somebody types `--sprint`. So the
default is floor, and an entry leaves the floor only for a named cost reason.

**The rule, stated once.** An entry is `floor` when its level-3 run needs no
`cargo`, no `npm`, no `wasm-pack`, no browser, no corpus and no GPU. Otherwise
it is `deep`, and it carries a level-1 probe in the floor as well so the
detection logic is still watched on every push. **A `needs` of `gpu`, `browser`
or `corpus` with a `profile` of `floor` is refused by the census**, so the
"no GPU-needing guard test in the floor" rule is a mechanism rather than a
convention.

**What lands where.**

| Profile | Gate | Contents |
|---------|------|----------|
| `--floor` | `guards` | Every text-level refusal: `content`, `prose`, `provenance`, `unsafe`, `deviations`, `backlog`, `skills`, `pins`, `ci`, the `bindgen` manifest and source passes, all four `device` greps, every `verify_ledger` branch, all three hooks, the `corpus_check` manifest and coverage refusals, plus level-1 probes for the toolchain-needing entries |
| `--sprint` and `--all` | `guards-deep` | The level-3 runs that need `cargo`, `npm` or `wasm-pack`: `nostd` end to end, `bindgen` host reachability, `native` step 4, the `wasm` size ceiling end to end, `packages` install and typecheck, the `lint` rule, the `ocelli-native` compile error |
| `--all` | inside the `oracle` gate, unchanged | The twelve faults in `tools/oracle/src/faults.mjs` and the browser environment refusals, adopted and not duplicated |

**Three findings that move work into the floor and are worth stating, because
each one looked like a `deep` entry and is not.**

1. **The corpus digest and presence refusals need no corpus.** Their subject is
   a manifest row against a file's SHA-256, and nothing in that path parses
   DICOM. The probe writes a two-row manifest and two files of ASCII into the
   sandbox. So probes 10 and 11 of the runbook, which the runbook could only
   run on a machine holding the corpus, become floor probes that run in CI. The
   real `corpus` gate still needs the corpus and stays out of the floor.
2. **The wasm size ceiling needs no wasm-pack.** `check_size` reads the largest
   `*.wasm` under `crates/ocelli-wasm/pkg` and compares it to a recorded
   baseline. The probe writes a file of the right length and a budget file with
   a small baseline. The ceiling arithmetic is watched in the floor and the
   build is not.
3. **Most of `scripts/package_check.py` needs no npm.** `check_manifest` and
   `check_tarball` are pure functions over a manifest dict and a list of names,
   and the refusal the file exists for, an advertised `exports` path absent
   from the tarball, is one of them. Those become floor level-1 probes with a
   synthetic name list. Only the consumer install, the node import, the two
   `tsc` resolutions and the publish dry run stay deep.

**The budget is a recorded measurement, not a guess.** This plan states no
runtime number, for the reason `scripts/pin_and_size_check.py` gives about the
size budget: "A budget invented before the first measurement would be either
meaningless or immediately wrong." The first run writes the observed wall clock
per profile into `ci/guard-probe-budget.json` with a tolerance, and a later run
that exceeds it fails and has to be re-baselined deliberately. Same file
carries the uncovered-refusal ratchet described below. If the measured floor
cost turns out to be unacceptable, the two levers in order are a shared sandbox
per guard file rather than per probe, which the design already does, and then a
process pool over several sandboxes, which is a later change justified by the
recorded number and not by a feeling.

### 6. R2 applied to a guard, with worked examples

**For a guard, the specification is what the guard is FOR.** Not what its code
currently does. A probe written from the code asserts the current regex, and it
will pass forever after the regex has been weakened to match. Three examples,
because this is the failure mode a reviewer has to be able to spot.

**`scripts/unsafe_allowlist_check.py`.** The spec is HLD 27.2 R5, transcribed
above: "No unsafe outside the allow-list (ocelli-wasm/src/ring.rs,
ocelli-core/src/cast.rs)". So `refuses` is "an `unsafe` keyword in a third
file", and the probe appends an `unsafe` block to a crate that is not one of
the two. The probe does **not** test `is_unsafe` as an identifier or `unsafe`
inside a doc comment, because those are facts about the current
comment-stripping regex rather than about R5, and a test asserting them would
survive the regex being deleted.

**`scripts/staged_content_check.py`.** The spec is `CLAUDE.md`'s hard rule:
"The pre-commit hook refuses staged DICOM by magic bytes as well as by suffix.
No allowlist." That sentence has three clauses and therefore three probes: a
file with the magic bytes and no suffix, a file with a DICOM suffix and
non-DICOM content, and a DICOM under a path somebody might plausibly want
exempted, which tests the third clause. The oracle-output refusal has its own
spec, in `corpus/README.md` and HLD story E22.3, and therefore its own entry.

**`scripts/no_std_check.py`.** The spec is D-09 and the crates' own
`#![cfg_attr(not(test), no_std)]`. So `refuses` is "a crate declaring `no_std`
whose resolved dependency graph reaches a `std` feature". The level-1 probe
feeds a recorded `cargo tree -e normal,features` transcript containing a
box-drawn `└── glam feature "std"` line. That is not an arbitrary fixture: it
is the exact shape whose anchoring bug made this script report `OK: 11 no_std
crate(s) reach no std feature` on a tree that was not clean, on its first run
in S01. A transcript fixture watches that branch on every push at no cost, and
the level-3 run in `guards-deep` watches the wiring.

**The review question**, for the microscope pass and for a human: **did the
probe's input come from the citation or from the guard's source.** That is
where the R2 risk lives. The `expect` fragment coming from the source is fine
and is deliberate.

### 7. Completeness, proved mechanically

Three checks, because none of them is sufficient alone.

**a. Refusal-site discovery.** `scripts/guard_census.py` scans `scripts/`,
`ci/`, `.githooks/`, `bin/` and `tools/` for the shapes a refusal takes in this
repository: `problems.append(`, a `sys.exit(` carrying a message, a `return 1`
inside a function that printed a `FAIL`, `echo "FAIL:` in shell, `exit 1` in
shell, and `throw new Error(` in the oracle's JavaScript. Every discovered site
must be claimed by exactly one catalogue entry. Matching is on the message
fragment rather than on `file:line`, so moving a refusal within a file does not
churn the catalogue and renaming a message does force a re-read.

**Strict in both directions**, which is the discipline `docs/lld/oracle.md`
already applies to `unsupported.json`: a site no entry claims fails the census,
so the catalogue cannot fall behind, and an entry no site backs also fails it,
so a deleted refusal cannot leave a stale entry that reads as coverage.

**b. Gate and hook coverage.** Every name in `bin/ocelli.sh`'s `GATES` array
must have at least one entry or an explicit `delegated` declaration with a
reason. `fmt` and `types` are `delegated`, to rustfmt and to tsc, because their
refusal is not ours to probe. The array is parsed with the same idiom
`scripts/ci_floor_check.py` already uses, so the repository has one parser for
that array and not two. Every executable under `.githooks/` must have entries.

**c. The declared-constant ratchet.** This is the answer to the class of
weakening no probe can reach, and it is the part of the design that most
directly addresses "a guard silently weakened by a refactor". A probe proves a
guard still refuses what it refuses. It cannot notice that the guard's own
configuration has been widened, because after the widening the guard is
correct about its new, weaker rule. So the catalogue records, per guard, the
constants that define its strictness:

| Guard | Constants recorded |
|-------|--------------------|
| `scripts/unsafe_allowlist_check.py` | `ALLOWED` |
| `scripts/staged_content_check.py` | `DICOM_SUFFIXES`, `ARTEFACT_PARTS`, `MAX_BYTES`, `ORACLE_OUTPUT_PREFIXES`, and the size-exempt suffix set |
| `scripts/prose_check.py` | `INCLUDE_PREFIXES`, `INCLUDE_EXACT` |
| `scripts/source_provenance_check.py` | `BLOCKED`, `BLOCKED_URLS`, `POLICY_FILES` |
| `scripts/pin_and_size_check.py` | `EXACT_PINNED`, `TOLERANCE` |
| `scripts/ci_floor_check.py` | `NOT_IN_FLOOR` |
| `scripts/verify_ledger.py` | `CORPUS_STATES` |
| `scripts/backlog_check.py` | `HOOK_EIDS`, `DECLARED_DEFECTS`, `VALID_STATUS` |
| `ci/check-device-ownership.sh` | `CREATORS` |
| `Cargo.toml` | the HLD 27.1 lint table, verbatim |
| `eslint.config.js` | the `NO_CACHED_WASM_VIEW` selector and its allowed file |

A change to any of these fails the census until the recorded value is updated
in the same change, which puts the widening in the diff and in front of a
reviewer rather than in a refactor nobody reads. The precedent is already here:
`unsafe_allowlist_check.py` says adding a path to `ALLOWED` "is a design-plan
decision with a recorded rationale, not an edit to this script made to get a
build green", and today nothing enforces that sentence.

**d. Forcing a guard added next month to arrive with its test.** The chain is
mechanical end to end and has no instruction in it. A new refusal in a scanned
file is discovered by (a), which fails `guard_census.py`, which runs in the
`guards` gate, which is in the floor, which `scripts/ci_floor_check.py` already
requires CI to invoke. So the author of the next guard sees red in CI on the
push that adds it. `.claude/commands/design.md` and `implement-feature.md` gain
a sentence as well, but the sentence is a courtesy and the census is the
mechanism.

**e. The uncovered ratchet, so the story can be honest about what it did not
reach.** The census counts around a hundred distinct refusal sites across the
repository. Writing a probe for every one of them inside three weeks is not
credible, and a plan that claimed otherwise would be the same kind of
overclaim this story exists to stop. So an entry may declare `probe: none` with
a reason and an owning F-ID, the census prints every one on every run in the
shape `scripts/corpus_tests.py` uses for a skip, and the count is recorded in
`ci/guard-probe-budget.json` as a ratchet that may only decrease. A new
uncovered refusal therefore fails the gate, and the backlog of uncovered ones
is visible on every run rather than forgotten. Whether the sprint profile
should additionally fail on any non-zero count is open question 5.

### 8. Adopting the oracle's catalogue rather than copying it

`tools/oracle/src/faults.mjs` already declares twelve faults and
`tools/oracle/tests/faults.mjs` already re-runs them on every oracle gate.
`scripts/guard_census.py` reads that file and counts its entries as coverage
for the oracle's boundary refusals. It does not re-declare them and it does not
run them, because the oracle gate already does and the run needs a browser.

The reason to adopt rather than copy is the one `CLAUDE.md` gives about the LUT
chain and tier C: a second copy behind a profile check is the same defect as a
second copy anywhere else, except that it only runs where nobody looks. One
catalogue with two backends, one of which is the existing JavaScript runner.

What the census still owns for the oracle is the refusals in `run.mjs` that no
fault reaches: the pin check, the output-directory refusal, the argument
refusals, and the frame-hash mismatch. It will also record whether
`tools/oracle/tests/paths_test.mjs` already covers the `isEntryPoint` defect
that runbook probe 24 describes, and add nothing if it does.

### 9. Implementation order

Sequenced by what breaks worst if it is silently broken, not by what is easiest.

1. **The sandbox, the choke point, the tripwire and the self test.** Nothing
   else is safe to write first.
2. **The D-04 chain.** Every branch of `scripts/verify_ledger.py`, all three
   hooks driven through real commits in the sandbox, and specifically the
   `check-commit` tree-mismatch branch, which is the load-bearing half of
   D-04's mechanism 2 and has never been observed red by anyone.
3. **Patient data and source policy.** `staged_content_check.py` and
   `source_provenance_check.py`, in full.
4. **The rest of the floor text guards**, and the census with its discovery
   scan and its two-directional claim matching.
5. **The declared-constant ratchet.**
6. **`guards-deep`** and the toolchain-needing level-3 runs.
7. **The generated probe table** in `docs/runbooks/guard-verification.md`, so
   the document and the executable stop being two things.

If the story runs long, items 6 and 7 are the ones to split into a follow-up,
and 1 to 5 still deliver the sentence in `CURRENT_SPRINT.md` for every guard
that costs nothing to probe.

### 10. Two hazards this plan has already hit, recorded so the implementation
does not rediscover them

**The catalogue must not trip the guards it describes.** Three real cases.
`scripts/source_provenance_check.py` refuses an unqualified mention of a
read-blocked project in any tracked text file, and a catalogue entry for that
guard has to name one. The fix is not an allowlist entry: each entry's
`refuses` sentence naturally sits within the checker's 200-character negation
window, because it says the project must not be depended on, which is what the
policy asks for anyway. Adding `scripts/guards/catalogue.py` to `POLICY_FILES`
is the fallback and it is worse, because widening a policy allowlist to make a
build green is the exact shape this repository distrusts. `prose_check.py` and
`deviation_check.py` are avoided by construction: neither scans `scripts/`,
which is a second reason the catalogue is Python under `scripts/guards/` rather
than a document.

**A design plan citing an undeclared deviation token is refused.**
`scripts/deviation_check.py` scans `.claude/plans/` for anything matching a
`D-` followed by two digits and fails when the row does not exist. The
runbook's row 5 names such a token as its probe, and this plan therefore
describes that probe in words rather than reproducing the token. The catalogue
entry writes it into the sandbox at probe time, which is the only place it is
safe.

## Boundary and tier

- wasm-bindgen: not touched. This story adds no crate and no manifest entry.
- Pixels across the boundary: no. Nothing here renders, decodes or compares a
  pixel.
- Render-loop allocation: none. No code in this story runs in a render loop.
- unsafe: none. No `.rs` file is added or modified, and the two permitted files
  are not touched.
- Tier A (WebGPU): n/a. The harness is repository tooling and resolves no tier.
  The oracle entries it adopts run under headless Chromium on SwiftShader,
  which is a software rasteriser and not a wgpu tier at all, and they stay
  inside the existing `oracle` gate.
- Tier B (WebGL2): n/a, for the same reason.
- Tier C (CPU, D-07): n/a, for the same reason. Recorded rather than omitted,
  because an omitted row and a deliberate "no CPU path" read identically later.

The one tier-shaped decision this story does make is the `needs` field, and it
is enforced rather than encouraged: an entry declaring `gpu`, `browser` or
`corpus` may not carry `profile: floor`, and the census refuses that
combination. That is `.claude/WORKFLOW.md`'s floor definition turned into a
mechanism.

## Decisions taken in the design round

Answers to `## Open questions`, taken in the S03 consolidated round.

**1. Two gates.** `guards` in the floor, `guards-deep` in `--sprint` and
`--all`. One gate would either put a toolchain in the floor or leave the deep
probes unrun, and the census rule that a `needs: gpu|browser|corpus` entry may
not be `profile: floor` is what keeps the split honest rather than habitual.

**2. `guards-deep` gets a CI job on `main` pushes and `workflow_dispatch`, not
on `pull_request`.** That is the strongest claim the cost allows, and the story
words it precisely: a weakened deep guard is caught on merge to `main` rather
than on the pull request.

**3. Generate the probe table in `docs/runbooks/guard-verification.md` between
markers, and leave the prose hand-written.** The table is a projection of the
catalogue and drifts the moment a guard is added, which is the defect this story
exists to fix. The prose around it is the author's reasoning and is not
generated. The `guards` gate carries the `--check`.

**4. The declared-constant ratchet covers the allow-lists and the path
prefixes, and records `MAX_BYTES` and `TOLERANCE` as tunable.** A tunable
constant still gets recorded, because the point is that a change is visible in a
diff, but it fails the census only on an unrecorded change rather than on any
change. `ORACLE_OUTPUT_PREFIXES` is in the ratchet, and both F-011 and F-X006
add a prefix to it this sprint, which is handled by decision 12 below.

**5. The uncovered ratchet fails the floor on growth, and fails `--sprint` on
any non-zero count once the sweep is complete.** That is the definition of done
for this story: the count reaches zero and the ratchet holds it there.

**6. No deviation row.** The HLD has no section on repository guards, so there
is nothing to depart from. The plan's Deviations section says "none" explicitly
rather than being absent.

**7. The scope boundary is confirmed: repository guards only.** The discovery
scan is rooted at `scripts/`, `ci/`, `.githooks/`, `bin/` and `tools/`, and not
at `crates/`. F-004's tier-unavailable path and F-005's panic mapping are
runtime behaviour belonging to their own stories' tests. Without that line the
story is unbounded and puts a second owner on files those stories are writing.

**8. Yes, ship the HLD 27.1 deny-list guard.** Nothing today asserts that the
denied lints are still denied, so a lint moved from `deny` to `allow`, or a
crate that stops carrying `lints.workspace = true`, is silent. That is a real
hole found by taking the census, and it is the same shape as the two guards the
S01 runbook exercise produced. It is one new guard and it arrives with its own
probe.

**9. The test category is `conformance`.** Naming a new `guard` category is a
`.claude/WORKFLOW.md` change and this story does not need one to be correct.

**10. Fix `CHANGELOG.md`'s stale gate count in this story.** It is the story
that changes the count, `prose_check.py` covers no part of that file, and S01
already found one stale count sitting there for exactly that reason. Whether the
unreleased section should be checked at all stays F-X010's question.

**11. The `core.hooksPath` enablement check belongs in `/verify`, not CI, and is
recorded rather than built here.** A hook is inert until a clone opts in, and
nothing checks it. `.claude/commands/verify.md` is not in this story's write
