## Normative source, transcribed

From `.claude/skills/dicom-expert/SKILL.md` section 8, multiframe and enhanced
SOP classes:

```text
(5200,9229)  SharedFunctionalGroupsSequence
(5200,9230)  PerFrameFunctionalGroupsSequence

The lookup order is per-frame first, then shared. An attribute present in
both is a malformed file, and per-frame wins.
```

Useful groups inside them include `PixelMeasuresSequence` (PixelSpacing,
SliceThickness). From the same skill's section 2: `FL` / `FD` are 32 and
64-bit float, binary, unlike `DS` and `IS`, which are strings. An FD value
never arrives as text, so the corner path needs a read path of its own for it.

From the story row, the acceptance intent preserved from the recovered draft:
slice thickness, kVp, mAs, TR and TE read from the shared and per-frame
functional groups for the shown frame, FD values formatted by one rule with a
fixture citing its PS3.3 macro, the top-level attribute first where both
exist, and a field that is absent from both left empty rather than guessed.

`docs/hld/24-agent-code-standards.md` 27.2 R3, via CLAUDE.md: every function
doing pixel arithmetic needs a fixture with hand-computed values citing its
DICOM section. The formatting fixture here cites the PS3.3 macro that declares
each attribute FD.

## Problem and evidence

`examples/folder-viewer/src/preview.rs`, `push_corner_fields` at line 3672 at
31323a79, reads the acquisition fields on the top-level object only. Its loop
pushes `sliceLocation`, `sliceThickness`, `kVp`, `repetitionTime` and
`echoTime` through `corner_decimal`, and exposure through `corner_text`, all
on the top-level `object`, with the tag constants at lines 95 to 114. An
enhanced CT or MR file keeps these in functional groups under FD, so those
corner lines are empty on such a file.

That is F-212's stated non-goal. `.claude/plans/F-212-design.md`, "Top level
only": "These acquisition fields are read from the top-level data set. An
enhanced CT or MR multiframe file keeps them in functional groups, under FD
VRs this preview does not read, and shows them empty rather than wrong. That
is a stated non-goal." Question 4 and the operator's answer of 2026-11-05:
"enhanced multiframe acquisition fields stay empty in this story, and a
follow-up story is filed by the sprint lead at /complete-feature."
`docs/sprints/AS_BUILT.md:5573`: "The follow-up story the plan's answer 4
asks the sprint lead to file, enhanced multiframe acquisition fields for the
corners, is not filed by this commit."

Reproducer. Open a synthetic enhanced CT multiframe whose Slice Thickness
lives only in a shared or per-frame `PixelMeasuresSequence` and read the
corner payload of the preview response. `sliceThickness` is empty today. The
synthetic file is generated by a committed script into ignored `corpus/data`,
never committed, in the dicom-tooling skill's pattern, with the expected
values computed by hand from PS3.3 and never from the implementation.

## Scope, API and compatibility

In scope: slice thickness, kVp, mAs, TR and TE read for the shown frame from
the shared and per-frame functional groups, the top-level attribute first
where both exist, FD formatted by one rule, and a field absent from both
places left empty. The read path lands where the design places it, in the
preview provider or in `ocelli-dicom`, and the corner payload keeps F-212's
field names and JSON shape so the page needs no change.

Non-goals: an enhanced Slice Location counterpart unless the design finds one
in PS3.3, per-frame window or VOI, palette or ICC, any change to classic
files' corners, exposure computed from tube current and exposure time, and a
new viewer page.

User-facing delivery. The fields surface through the existing viewer front
door, the same corner payload and provider contract F-245 and F-202 consumers
use. A Rust-side helper alone is not end-user acceptance, and no second
viewer is created. The visible result is the corner lines on the page the
viewer already renders.

## Consumer and provider map

| Consumer / entry point | Concrete provider | Caller context / policy | Observable output |
|------------------------|-------------------|-------------------------|-------------------|
| Folder viewer corners | `push_corner_fields` and the frame metadata provider | Once per shown frame | The corner payload with the five fields and exposure |
| Showcase viewer consumers | The same provider through the shared contract | Same fields, same units, same absent-field rule | The same payload in the single viewer |
| `ocelli-dicom` metadata | The functional group reader, if the design places it there | Per-frame first, then shared, top-level first where both exist | Typed values or an absent field |

## State transitions and invariants

Frame change: the shown frame's own functional groups are read, never the
first frame's. A field absent from the top level and from both group levels is
empty, never guessed and never carried from the previous frame. Invariant: the
corner values shown belong to the frame on screen.

## Ownership, commit and recovery

Not applicable in the render-loop sense. The read is per frame-open, the
values are derived and not cached across files, and a malformed functional
group is a named refusal or an empty field, never a stale value.

## Approach

1. Transcribe the exact functional group sequences and attributes from
   PS3.3 for enhanced CT and enhanced MR, with both precedence rules, before
   any code.
2. Add the FD read path where the design places it, with the one formatting
   rule and its fixture.
3. Wire the corner payload for the shown frame, reusing F-212's field names
   and JSON shape.
4. Synthetic fixtures from a committed generator, expected values computed by
   hand from PS3.3.

Rejected: reading every group eagerly at parse time, a second corner payload
shape for enhanced files, and inferring Slice Location from plane position,
which F-212 deliberately does not do.
