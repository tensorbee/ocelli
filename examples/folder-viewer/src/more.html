Images More Use

Features and the road ahead

The viewer is Ocelli's showcase. A feature is implemented here only when it has a usable workflow on Images. Library code without that workflow is shown separately.

This is the S46 integration preview. Sprint acceptance and performance measurements are still in progress. Another running build can show an older feature list.

Implemented means usable in this viewer, with the limits named. Partial means a working part exists and the missing part is stated. Not yet means the viewer workflow is absent, even when its library is built. Planned is future work and is never presented as an implemented advantage.

The comparison uses the inspected Cornerstone3D 5.8.2 core, tools and DICOM loader as the tested baseline, checked 8 November 2026. Cornerstone supplies library APIs. A host application still supplies workflows such as prior-study search and saved preferences. Current ecosystem capabilities are identified explicitly.

Rendering support depends on the device: A is WebGPU, B is WebGL2 and C is CPU. An unavailable tier is named in the viewer. A working GPU path is not a promise of a CPU implementation. A checked API is not a claim of pixel or performance parity.

Overlay planes and display shutters

Not yet in the viewer. The overlay and shutter reader is built.

An overlay plane is a one bit graphic stored beside the image, such as a marker or a region of interest drawn by the modality, PS3.3 C.9.2. A display shutter masks part of the image that should not be shown, often the collimated edge of a radiograph, PS3.3 C.7.6.11.

Lives in ocelli-dicom, crates/ocelli-dicom/src/overlay.rs. read_overlays returns an OverlaySet for one frame.

Library API details 
use ocelli_dicom::{parse_part10, read_overlays, ShutterShape};

let parsed = parse_part10(bytes)?;
let set = read_overlays(&parsed, 0)?;          // frame 0

for plane in set.planes() {
    let group = plane.group();                   // an even group from 0x6000
    let kind = plane.overlay_type();             // OverlayType::Graphics or Roi
    let on = plane.bit(row, column);             // 1-based image pixel
}

if let Some(shutter) = set.shutter() {
    let hidden = shutter.hides(row, column);     // shapes combine by intersection
    for shape in shutter.shapes() {
        match shape {
            ShutterShape::Rectangular { left, right, upper, lower } => {}
            ShutterShape::Circular { center_row, center_column, radius } => {}
            ShutterShape::Polygonal { vertices } => {}
            ShutterShape::Bitmap { group } => {}
            _ => {}                              // non_exhaustive
        }
    }
}
let grey = set.presentation_value();             // Shutter Presentation Value, when present

Tiers A, B and C do not draw this module. The reader does not decode Pixel Data. The example page posts a synthetic object and prints whether one pixel is set and whether the shutter hides it.

Interpolation between pixels and between slices

Partial. The viewer uses nearest sampling. The library also supports linear, but the viewer has no interpolation selector.

When an image is zoomed, each screen pixel falls between stored pixels. Nearest shows the closest stored value, which keeps edges hard. Linear blends the four neighbours, which looks smoother but is no longer a stored value. A reader should know which one is on.

Lives in ocelli-render, crates/ocelli-render/src/interpolation.rs. Interpolation is Nearest or Linear, and available(mode, tier) answers before a draw.

Library API details 
use ocelli_render::{available, Interpolation, Tier};

let mode = Interpolation::Linear;
if available(mode, resolution.caps.tier) {
    graph.set_stack_interpolation(&ctx, viewport, mode)?;   // tiers A and B
}
raster.set_interpolation(mode.mode())?;                       // tier C, CpuRaster

Sampling between two slices is a volume operation. Volume::reslice takes a fractional slice index and reads it through the volume's trilinear sample, shown under MPR below. A stack mode that blends slice n with slice n + 1 on screen is not built.

Nearest and linear are available on tiers A, B and C. Linear on an orthographic plane is refused rather than drawn as nearest.

Reference line and reference cursor

Partial. Reference lines work in the viewer. A shared patient-point cursor is not yet exposed.

A reference line shows where the slice in one viewport cuts the image in another, so a reader can tell which axial level a coronal line is at. A reference cursor marks the same patient point in every viewport.

The line where one image plane cuts another lives in ocelli-viewport as link::reference_segment, which the image page of this folder viewer draws its reference lines with through the local process. A crosshair or a reference cursor lives in @ocelli/core, packages/core/src/crosshair.ts and packages/core/src/intersection.ts, where overlayGrid lives. Those functions take a point already projected into viewport pixels and return segments for the SVG layer.

Library API details 
import { crosshairLines, overlayGrid, referenceCursor, referenceLines } from "@ocelli/core";

// x and y are viewport pixels. Null when the point is outside the viewport.
const lines = referenceLines(x, y, width, height);   // [horizontal, vertical] Segments
const cursor = referenceCursor(x, y, width, height); // { x, y } or null
const cross = crosshairLines(x, y, width, height);   // the same two segments
const grid = overlayGrid(2, 2, width, height);       // interior lines of a layout grid

for (const { x0, y0, x1, y1 } of lines ?? []) {
  // append an SVG line element
}

The shell functions do not project a plane and do not read a frame of reference. reference_segment projects the plane, and the geometry chapter of Use shows it. It is CPU arithmetic and runs the same on every tier, as the shell code does.

Several series at once

Partial. Multiple viewports and linked scroll, window and zoom work. Prior-study selection is not yet built.

Reading often means two series side by side: a current scan beside a prior, or two sequences of the same MRI. Scrolling one should move the other to the same anatomy, and a window change may apply to both.

Lives in ocelli-volume as HeldPlane and in ocelli-viewport as sync::SyncScene and link. A scene moves every viewport that shares the source's Frame of Reference UID onto one patient point. link::closest_coplanar chooses the nearest image in a stack of planes that need not be uniform, which is what the image page scrolls with.

Library API details 
use glam::DVec3;
use ocelli_core::{Pt, World};
use ocelli_viewport::sync::SyncScene;
use ocelli_volume::{FrameOfReferenceUid, HeldPlane};

let mut scene = SyncScene::new();
let plane = HeldPlane {
    anchor: Pt::<World>::new(0.0, 0.0, 0.0),  // world point of index 0
    normal: DVec3::new(0.0, 0.0, 1.0),
    spacing_mm: 2.5,
    index: 0.0,
};
scene.register(1, Some(FrameOfReferenceUid(uid.clone())), plane);
scene.register(2, Some(FrameOfReferenceUid(uid.clone())), other_plane);

// Viewport 1 moved to this point. Every peer with the same UID follows.
for change in scene.set_point(1, point)? {
    let (id, index) = (change.id, change.index);
}

A different Frame of Reference UID stays where it is, and a refused point is SyncError::Unavailable with no slot written. attachSideBySide(ocelliElement, neighbour) in @ocelli/core pairs an Ocelli element with an element another library owns and enables the seam, which is the migration case rather than a second series.

The image page of this folder viewer lays out 1 by 1 up to 3 by 3 viewports, each with its own series, image, zoom and window, and a series row dragged onto a viewport opens there. Its Link menu turns on linked scroll, synced window and synced zoom over every visible viewport, through ocelli_viewport::link in the local process. Not built: linked scroll and synced window as features of the npm run dev example, and prior study lookup. That example page reads Prior studies, Linked scroll and Synced window unavailable.

MPR

Not yet in the viewer. Orthographic and oblique MPR are built in the library.

Multiplanar reformation rebuilds sagittal, coronal or any oblique plane from a stack of axial slices, so anatomy can be seen in the plane that shows it best. It depends on correct spacing and orientation, which is why a sheared stack is refused rather than straightened.

Lives in ocelli-volume, crates/ocelli-volume/src/ortho.rs, with presentation in ocelli-render, crates/ocelli-render/src/ortho.rs.

Library API details 
use ocelli_volume::{ObliquePlane, OrthoPlane, PlaneSample, Volume};

let volume = Volume::construct(candidate)?;

let axial    = volume.reslice(OrthoPlane::Axial    { slice: 10.5 })?;   // fractional is allowed
let sagittal = volume.reslice(OrthoPlane::Sagittal { column: 256.0 })?;
let coronal  = volume.reslice(OrthoPlane::Coronal  { row: 256.0 })?;

let oblique = volume.reslice_oblique(ObliquePlane {
    origin, row, column,            // Pt<World> and two DVec3 directions
    columns: 512, rows: 512,
    column_mm: 0.7, row_mm: 0.7,
})?;

for sample in &axial.samples {
    match sample {
        PlaneSample::Present(value) => {}
        PlaneSample::Absent => {}  // a slice not landed or outside, never stored zero
    }
}
Library API details 
use ocelli_render::{present_cpu_plane, present_plane};

present_plane(tier, &axial, |samples| upload(samples))?;                      // tiers A and B
present_cpu_plane(&mut raster, &view, &presentation, &axial, quality, &mut out)?; // tier C

Tiers A and B present through present_plane and RenderGraph::show_ortho. Tier C presents through present_cpu_plane into CpuRaster. An absent sample or a raster refusal writes nothing.

Slab

Not yet in the viewer. The library draws slabs on GPU tiers A and B. CPU reduction is unavailable.

A slab collapses a thick block of slices into one image. Maximum intensity projection makes contrast filled vessels or lung nodules stand out, minimum intensity projection shows airways, and an average reduces noise.

The plane and samples live in ocelli-volume, crates/ocelli-volume/src/slab.rs. The reduction is a shader in ocelli-render, chosen by BlendMode, and it reduces modality values, because stage 1 is applied before the block is staged.

Library API details 
use ocelli_render::BlendMode;
use ocelli_volume::OrthoPlane;

let frame = volume.slab_plane(OrthoPlane::Axial { slice: 40.0 })?;
let image = volume.slab_samples(frame, 10.0)?;            // thickness in mm

graph.show_slab(&ctx, &adapter, viewport, &image, BlendMode::Mip)?;
// BlendMode::MinIp and BlendMode::Average are the other two reductions.

MIP, MinIP and average reduce stored samples and then apply the one existing VOI stage. Tiers A and B draw it. Tier C returns unavailable, because there is no CPU reducer.

Volume rendering

Not yet in the viewer. The library has GPU volume rendering. CPU volume rendering is unavailable.

Volume rendering casts a ray through the whole volume and accumulates colour and opacity, so a reader sees bone, vessels or an organ surface in three dimensions. It is for orientation and communication, not for measurement.

Lives in ocelli-render, crates/ocelli-render/src/graph.rs, with OpacityTable in opacity.rs, ShadeWeights in shade.rs and ClipPlane in clip.rs.

Library API details 
use ocelli_render::{volume_ray_admission, OpacityPreset, OpacityTable};

// Answer before any sample is read.
volume_ray_admission(tier, ready_bricks, sampled_limit)?;   // Err(TierCUnavailable) on tier C

let report = graph.sync_volume(&ctx, &adapter, volume_id, &volume)?;  // upload ready bricks
graph.bind_volume_ray(&ctx, &adapter, viewport, source)?;           // a VolumeRaySource
graph.set_opacity(&ctx, viewport, &OpacityTable::preset(OpacityPreset::Ramp))?;
graph.set_shade(&ctx, viewport, &weights)?;
graph.set_clip_planes(&ctx, viewport, &planes)?;
let outcome = graph.tick(&ctx);

Tiers A and B run the fragment ray. Tier C returns TierCUnavailable from volume_ray_admission before a sample is read and writes no colour. There is no CPU ray and the ray has no MIP body.

Fusion

Not yet in the viewer. The library has same-frame-of-reference GPU fusion.

Fusion lays one modality over another in the same patient space, most often PET colour over CT grey, so uptake can be placed on anatomy. The two volumes must share a frame of reference, or the overlay is in the wrong place.

The plane lives in ocelli-volume, crates/ocelli-volume/src/fusion.rs. The draw lives in ocelli-render, crates/ocelli-render/src/fusion.rs.

Library API details 
use ocelli_render::{FusionError, FusionRequest};
use ocelli_volume::{plane_from_ortho, world_on_plane, OrthoPlane};

let Some(plane) = plane_from_ortho(&ct, OrthoPlane::Axial { slice: 60.0 }) else { return };
let corner = world_on_plane(&plane, 0, 0);       // Pt<World> of one plane pixel

let request = FusionRequest {
    volume_a: &ct,  frame_a: &ct_frame,  chain_a: &ct_chain,  opacity_a: 1.0, colormap_a: None,
    volume_b: &pet, frame_b: &pet_frame, chain_b: &pet_chain, opacity_b: 0.5, colormap_b: Some(hot.as_slice()),
    plane: &plane,
};
match graph.show_fusion(&ctx, &adapter, &request) {
    Ok(()) => {}
    Err(FusionError::FrameMismatch) => {}     // the two UIDs differ
    Err(FusionError::TierCUnavailable) => {}
    Err(other) => {}
}

Tiers A and B draw it when a float sample format and the Rgba16Float target can be bound, and otherwise return FusionError::Unavailable. Tier C returns FusionError::TierCUnavailable before a sample is read.

Histogram

Not yet in the viewer. Histogram calculation is built.

A histogram counts how many pixels fall in each value range. It helps choose a window, shows whether an image is clipped, and summarises a region.

Lives in ocelli-geom, crates/ocelli-geom/src/stats.rs. The counts go into a buffer you own.

Library API details 
use ocelli_geom::{histogram, roi_statistics};

let mut counts = [0_u32; 256];
let range = histogram(&samples, &mut counts)?;   // samples: &[f64]
let (low, high, bin) = (range.min, range.max, range.width);

let stats = roi_statistics(&region, area_mm2)?;   // count, mean, sd, min, max, area

This is plain arithmetic and runs anywhere. A value on an interior edge belongs to the higher bin. No viewport or shell control draws a histogram. The example page reads Histogram unavailable, and the HLD's GPU histogram pass is tier A only.

Automatic window

Implemented in the viewer for a series that stores no window.

An image can store no Window Center, no Window Width and no VOI LUT Sequence. DICOM leaves the window to the viewer then, and open_frame still invents nothing. The automatic window is a labelled choice: the 1st to the 99th nearest-rank percentile of the modality values, PS3.3 C.11.1, each frame through its own rescale, with stored zero and that frame's Pixel Padding Value range, PS3.3 C.7.5.1.1.2, left out, drawn as LINEAR_EXACT, PS3.3 C.11.2.1.3.2. A frame of one value is drawn mid grey. A frame of padding and zero only is drawn at the output minimum, which is black on MONOCHROME2 and white on MONOCHROME1, PS3.3 C.7.6.3.1.2.

Lives in ocelli-pixel, crates/ocelli-pixel/src/auto_window.rs. series_sample(n) picks up to 16 images spread through a series, first and last included. AutoWindowPool pools them under a cap of 2^20 samples split equally between them, and auto_window is a pool of one image.

Library API details 
use ocelli_pixel::{AutoWindowPool, auto_window, series_sample};

let picked = series_sample(images)?;            // up to 16 indices
let mut pool = AutoWindowPool::new(picked.len())?;
pool.add_frame(&stored, &modality, padding)?; // once per picked image
let window = pool.finish()?;                    // centre, width, basis, counted
let one = auto_window(&stored, &modality, padding)?;

The image page draws every image of such a series at one window from its sampled images, so scrolling keeps relative brightness between slices, and the corner says Auto window. A thumbnail, and a series whose window the local process refuses, are drawn at each image's own automatic window, and the corner then says Auto window, this image. A window in the file is always used as it is. cornerstone3D 5.8.2 takes each image's own minimum and maximum instead, so this is a viewer policy and not a parity row, and the oracle keeps its own declared default.

The window is computed once on the host. Tier C draws it with the one CPU LutChain. Tiers A and B take the same centre and width through AutoWindow::transform and VoiParams::from_chain, and no GPU consumer calls the pool yet.

Metadata browser

Partial. Headers can be browsed and filtered. Recursive browsing, comparison and copy workflows remain.

A metadata browser lists every attribute of an instance by tag, keyword and value. It answers questions the image cannot, such as which kernel was used or why the spacing looks wrong.

Lives in ocelli-dicom, crates/ocelli-dicom/src/metadata.rs. MetadataSet holds tags in order, and each MetadataElement carries a VR and a typed MetadataValue.

Library API details 
use ocelli_dicom::{MetadataSet, MetadataValue, Tag};

let metadata = MetadataSet::from_object(parsed.object())?;

for (tag, element) in metadata.iter() {
    let text = element.semantic_text();       // Option<Vec<&str>>
    match element.value() {
        MetadataValue::Sequence(items) => {}  // nested MetadataSet values
        MetadataValue::PersonNames(names) => {}
        MetadataValue::BulkDataUri(uri) => {}
        _ => {}
    }
}
let modality = metadata.get(Tag(0x0008, 0x0060));

The same model is what QIDO-RS JSON parses into. The image page has a Headers panel. The example viewer reads Metadata browser unavailable.

Conformance report

Implemented in the viewer through the local process, within the report's stated scope. Browser-only generation remains planned.

A viewer that reads only the attributes it draws can show a file that breaks the standard, and another viewer can then refuse the same file. An age with no unit letter, a name longer than its limit and a mandatory attribute left empty all draw. The conformance report names such faults without stopping the image.

It checks the values of every element against PS3.5 Table 6.2-1, the value count of the attributes it lists against PS3.6, and the presence of Type 1, 1C, 2 and 2C attributes of seven PS3.3 modules on CR, CT, MR and PET Image Storage. It does not check Enumerated Values or Defined Terms, attributes inside a sequence for presence, any other SOP class for presence, enhanced or multi-frame IODs, or a condition the data set cannot decide, which it names instead. It is not proof that a file conforms to DICOM, and it says so in its first line: "This report checks the rules it lists and nothing else. It is not a statement that the file conforms to DICOM." A finding names a length, a count or a character position and never a value.

Lives in ocelli-dicom, crates/ocelli-dicom/src/conformance.rs, and its reader in @ocelli/core, packages/core/src/conformance.ts.

Library API details 
use ocelli_dicom::{check_conformance, parse_part10};

let report = check_conformance(&parse_part10(bytes)?);
let count = report.findings().len();
let json = report.to_json();               // read by readConformanceReport

Tiers A, B and C are not applicable, because the report reads attributes and no pixel, and it is the same on every tier. The image page shows the count on the Headers button and the findings in Checks on the Headers sheet. The report is made by the local process, because no wasm module links the parser yet.

One to one

Not yet in the viewer.

One to one shows each stored pixel as exactly one screen pixel, so nothing is resampled and fine texture is seen as acquired.

There is no code for it. A Zoom command in @ocelli/core scales the camera by a factor, and nothing computes the factor that maps one stored pixel to one device pixel.

Library API details 
import { packCommands, viewportId } from "@ocelli/core";

// What exists: an explicit zoom factor. It is not a one to one mode.
packCommands(viewportId(1), [{ kind: "Zoom", factor: 2 }]);

The example page reads One to one unavailable.

Preferences

Partial. Four choices are saved. General viewing, tool and layout preferences remain.

Preferences keep a reader's choices between sessions, such as default window presets, tool bindings and hanging layouts.

The image page keeps four choices in this browser, the mouse profile, the play rate and whether each of the two side columns is hidden. There is still no preferences module in the crates or packages.

JPEG XL and the transfer syntaxes

Partial. Two JPEG XL syntaxes decode, including supported RGB frames. JPEG recompression is refused.

The decoder registry knows nineteen transfer syntaxes and six registration functions cover them: raw and RLE Lossless together, JPEG, JPEG 2000, JPEG-LS, HTJ2K and JPEG XL. Seventeen have a decoder. Two do not. Deflated Explicit VR Little Endian deflates the whole data set rather than one frame, PS3.5 A.5, and JPEG XL JPEG Recompression is left unregistered because jxl-jbr 0.2.1 panics in the DHT branch of JPEG reconstruction, which is jxl-oxide issue 512, so a .111 frame is refused before any byte reaches jxl-oxide. JPEG XL Lossless and JPEG XL decode through jxl-oxide 0.12.6, and this folder viewer registers all six families, so its preview draws the supported monochrome and RGB frames. An empty Basic Offset Table, which PS3.5 A.4 requires decoders to accept, opens under every encapsulated syntax with a decoder, and frames that span Fragments are split at their JPEG or JPEG 2000 start and end markers only where both markers and the frame count prove the boundary, so RLE and JPEG XL frames split across Fragments are refused by name. cornerstone3D 5.8.2 cannot decode any of the three JPEG XL syntaxes, so the differential oracle has no reference frame for those rows, and their correctness comes instead from round trips against the synthetic sources, exact for the two lossless rows and worst-pixel bounded for the two lossy ones, which libjxl encoded. JPEG-LS follows T.87's run mode, which the vendored decoder now does under a recorded patch, and refuses any LSE preset it does not apply rather than drawing the frame with other coding parameters.

Tiers A, B and C decode on the CPU and do not select different registry behaviour.

Worker decode and the wasm path

An embedding page uses default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; connect-src 'self' on every response, the worker script included. See Load the core in a worker. This folder viewer is served under a policy with hashes for its inline scripts and styles and no 'wasm-unsafe-eval', because it decodes in the local process.

Not yet in the viewer. The local process decodes images. The browser worker fetch and transfer foundation is built.

In the browser path, the DICOM bytes go to a worker that owns the wasm core, and decoded pixels stay there. The main thread keeps the DOM responsive. This folder viewer posts each file once while the local process holds it, and posts it again after eviction or a restart. Opening another folder tells that process to forget the previous folder's files and frames through POST /forget. Leaving the page sends one short beacon naming the page, and the process forgets every file that page posted. A file of the active series rewritten on disk after the folder was opened is forgotten too, once the browser refuses to read it at the next focus, return to the page, series selection or change of active viewport, and a rewrite that keeps the modification time is not detected. It is still not the wasm path. The library's decoded tier, ImageCache, answers a lookup only for the bytes, description and plane a frame was decoded from, and the worker path still holds no frame cache. postWadoInstance passes its optional cache to DicomwebClient, whose default is "no-cache".

Lives in @ocelli/core: postWadoInstance in instance-bytes.ts, holdSessionBytes in bulk.ts, and openDecodePool in pool.ts.

Library API details 
import {
  DEFAULT_DECODE_WORKERS, MAX_DECODE_WORKERS, holdSessionBytes, openDecodePool, postWadoInstance,
} from "@ocelli/core";

// Main thread: one WADO-RS instance, posted to the worker as a transfer.
await postWadoInstance({
  studiesServiceUrl, wadoUriUrl, fetch: globalThis.fetch.bind(globalThis),
  studyUid, seriesUid, instanceUid,
  post(bytes, boundary) {
    worker.postMessage({ type: "instance", bytes: bytes.buffer, boundary }, [bytes.buffer]);
  },
});

// Worker: copy the body into the session's one bulk slot. It is not parsed here.
ticket = holdSessionBytes(wasm, new Uint8Array(message.bytes), ticket);

// Several decode workers, each its own wasm instance. No SharedArrayBuffer.
const pool = openDecodePool(owner, DEFAULT_DECODE_WORKERS, (index) => new Worker(url));
pool?.close();

Built: the bounded fetch, the hand-off, the bulk slot, a pool of one to MAX_DECODE_WORKERS workers with threadingEscalation() fixed at "stable", and the render session's own frame cache. Not built: decoding that envelope in the worker and a render of that frame. The decode workers own their instances and no session cache of their own. The example worker publishes one stored sample to prove the path. The session's releaseSeries releases a series from that cache and reports it as cache.released.

Documents

Partial. Save and reopen of marks and key images work. Further document and export workflows remain.

A measurement is useful beyond the session only if another system can read it. DICOM SR TID 1500 carries measurements, a Key Object Selection flags the images that matter, and a Secondary Capture stores a rendered picture as an image.

Lives in packages/core/src: tid1500.ts, measurement-persist.ts, annotation-state.ts, tid2010.ts and secondary-capture.ts. The tree they share is sr.ts.
